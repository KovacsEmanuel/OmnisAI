## Review independent: motive de NO-GO și controale noi

Review-ul independent a identificat trei riscuri: `urllib` urma redirecturi HTTP spre un sink înainte de verificarea originului; un API propriu fără port sănătos bloca cleanupul DB; network membership runtime nu verifica faptul că numai API intră pe front. RED a reprodus redirectul către un sink **sintetic loopback** (`200` în loc de `302`), cleanupul blocat de `NetworkSettings.Ports={}` și DB atașată fals la front acceptată. GREEN: redirecturile sunt refuzate înaintea cererii suplimentare, identitatea resursei pentru cleanup este separată de readiness, iar rețelele containerelor sunt comparate exact per serviciu. Un control suplimentar cu membru străin pe rețea cere oprirea numai a containerelor proprii atestate și verdict **incomplete**, fără `compose down` peste membrul străin. Un copil real rezistent la TERM a demonstrat RED supraviețuirea după timeoutul lui `subprocess.run`; harnessul folosește acum un process group TERM→KILL și păstrează un rezultat Docker daemon-side incert ca **OUTCOME_UNCERTAIN**, nu `STOPPED`. Aceste teste nu sunt un sandbox/garanție față de root ori același UID.

**Blocaj host decisiv:** [documentația oficială Docker despre port publishing](https://docs.docker.com/engine/network/port-publishing/) avertizează că în Engine **<28.0.0** un port publicat pe localhost poate fi accesat de gazde din același segment L2. Hostul probei are `27.5.1+dfsg4`; prin urmare testul pozitiv de mai sus **nu certifică absența LAN exposure**, chiar dacă bindul inspectat era `127.0.0.1`. Nu avem captură de la un peer L2 controlat pentru a exclude accesul anterior și nu afirmăm că niciun peer nu l-a putut atinge. Am adăugat gate fail-closed `validate_docker_engine`: `27.5.1+dfsg4` este refuzat, `28.0.0` este doar eligibil pentru **probe negative ulterioare**, nu aprobat implicit. `make check-installed-control` pe hostul curent a ieșit **2** la acel preflight după gate-ul non-startup, înainte de image build/container nou.
