**Parțial / G00 deschis.** Experimentul este pe `p04-control-topology-wip`, pornit din `main` la `c4cb784`; nu este încă `omnis start`, `pair`, `open` sau `stop`. ## Contract exercitat, nu launcher de produs

`ops/compose.control.yaml` nu mai declară niciun port publicat și nu mai are bridge `front`. DB, supervisor și API sunt numai pe rețeaua `control` cu `internal: true`. API-ul din wheel/OCI fixează un singur listener AF_UNIX `api.sock` într-un bind separat `0700`, deținut de UID-ul operatorului, socket `0600`; `control.sock` rămâne în alt bind, iar Docker socket nu este montat. Uvicorn 0.54 ar seta implicit `0666` pe calea `--uds`, de aceea `omnis.serve` pre-leagă socketul 0600, îl predă ca FD lui Uvicorn și elimină numai inode-ul propriu la shutdown. Testul procesului real a surprins RED că Uvicorn re-emite SIGTERM după drenare, ocolind cleanupul; signal handlerul buclei previne uciderea înaintea eliberării inode-ului. Testele API pe UDS: 3/3, inclusiv HTTP live, Host greșit refuzat, mod/owner și symlink negativ. Wheelul API actual a încărcat modulul `omnis.serve` din arhivă, din afara checkoutului.

Hostul are un forwarder CLI mic, pornit numai la acțiunea explicită a harnessului: listener `127.0.0.1:<port>` → unicul UDS privat, verificând modul/UID-ul peer-ului cu `SO_PEERCRED`, limita de bytes/deadline și fără interpretarea sau rescrierea Host/Origin. Testele CLI de forwarder sunt 3/3: cererea reală ajunge la peer, un port străin nu este adoptat și procesul se oprește cu readback. Nu este încă integrat într-o comandă operator; proba de cod nu atestă singură două launchuri/lock/PID stale sau un browser real.

Într-un control disposable fără DB/HTTP externe, imaginea Python pin-uită a creat un socket Unix montat, accesibil de pe host cu UID mapat și 0600, `--network none`, fără porturi; răspunsul HTTP sintetic a păstrat Host exact. `PRIVATE_UDS_PROBE_OK` și cleanupul containerului/numele propriu au avut exit 0, cu readback; scriptul `hermes-verify-*` a fost eliminat. Acesta este un spike de fezabilitate, **nu** un test al aplicației Omnis.

## Remedieri după review-ul forwarderului host

Review-ul independent read-only a găsit trei P1 și o limită de teardown în `omnis_cli.forwarder`. Un asset valid de 2 MiB era trunchiat înaintea antetelor complete (RED `IncompleteReadError`); limita rămâne per conexiune și finită, dar este distinctă: 2 MiB browser→API, 16 MiB API→browser pentru asset/antete și răspunsuri HTTP succesive pe keep-alive. RED cu 20 clienți idle a creat 20 conexiuni UDS; acum contorul de admitere serializat în event loop permite maximum 16 handler-e active înaintea primei operații `await`, iar surplusul este închis fără UDS. `Server.close()` singur nu drena clienții acceptați (RED `wait_closed` timeout); ownerul listenerului urmărește și anulează taskurile proprii la oprire și așteaptă bounded închiderea lor.
