### R2-80-01 — MEDIUM — TLS handshake failure does not close the broker stream; handshake EOF also escapes the transport taxonomy

**Source:** `api/src/omnis/supervisor/model_sender.py:60–76,105–112,240–268`; `api/src/omnis/supervisor/model_relay.py:213–217`; `cli/src/omnis_cli/model_relay.py:127–129`; runtime `model_test_runtime.py:50–53,254–255,579–595`.

`Backend.connect_tcp` has already OPENed a broker connection and returns a `CipherStream`. `Stream.start_tls` directly awaits `TLSStream.wrap`, with no close-on-handshake-failure. The former public httpcore AnyIO adapter explicitly closed its raw stream on TLS failure and mapped expected handshake errors. The replacement does neither. A certificate verification failure can therefore leave an open host socket/current broker connection after an ordinary FAILED Refresh. The next fresh OPEN is rejected by the broker's one-live-stream check, and `Relay.rpc` treats DENIED as a fatal control failure. This converts an ordinary upstream/TLS failure into permanent `settlement_failed` / CONTROL_UNAVAILABLE until owner restart.

There is also a direct exception path: the installed AnyIO `streams/tls.py:182–220` converts an unexpected TLS EOF into `EndOfStream` when `standard_compatible=False`. EOF during `wrap` is outside `Stream.read`'s EndOfStream catch. `metadata()` and `refresh()` do not catch that exception; the metadata task faults and `finished()` poisons the owner even if persistence succeeded. The built-in httpcore adapter's `start_tls` maps `anyio.EndOfStream` to `ConnectError` and closes the underlying stream (`httpcore/_backends/anyio.py:55–80`); the generic httpcore connection merely sets `_connect_failed` on this exception, not the missing CipherStream close (`_async/connection.py:99–101`). These dependency files were read from the existing project venv, not imported or executed.

**Minimal reproducer for parent:** same existing real broker/TLS fixture, no new harness: (a) a trusted-origin server presents the wrong hostname/untrusted certificate, or (b) accepts TCP then closes during ClientHello/handshake. Observe the first Refresh's readable FAILED receipt, broker stream lifetime, `owner.settlement_failed`, and an explicit healthy Refresh with a new command after restoring the peer. No automatic retry. The current `metadata_eof` case closes only after completing TLS and reading the HTTP request (`test_model_test_v2.py:174–193`), so it does not cover this path.

**Minimum remedy:** retain ownership of the raw stream through handshake failure, explicitly fence/drain/close it, and normalize only expected TLS/network/EOF failures at this existing public transport boundary. Keep RelayFailure/control uncertainty fatal; do not swallow cancellation or DB failures. Add one handshake-cut recovery case to the existing consumer test.

### R2-80-02 — MEDIUM — ordinary DNS failure is mislabeled DENIED and leaves OPEN live, permanently faulting the owner

**Source:** `cli/src/omnis_cli/model_relay.py:127–161,215–226`; `cli/src/omnis_cli/forwarder.py:220–223`; `api/src/omnis/supervisor/model_relay.py:126–131`; runtime `model_test_runtime.py:50–53,254–255,584–595`.

The resolver catches `socket.getaddrinfo` OSError and deliberately leaves `rows=[]` as an ordinary upstream refusal. `auth_addresses(rows)` then raises `ValueError("Empty auth DNS answer")`, not OSError. The broad ValueError branch keeps the initial status DENIED and closes only WRITE connections, so this OPEN's `Connection.closed` remains false. The authenticated broker is healthy, but the sender interprets DENIED as `RELAY_CONTROL_UNCERTAIN`, sets `relay.failed`, and permanently faults the execution owner. Even an isolated subsequent OPEN encounters the still-live connection and is denied as busy.

**Minimal reproducer for parent:** existing broker fixture: make the first `getaddrinfo` raise `socket.gaierror`; explicit metadata Refresh; restore DNS and issue a fresh Refresh command. Expect a sanitized failed upstream attempt and then healthy explicit recovery, with no implicit second lookup/retry. Current held-DNS tests return a valid answer after release; they do not exercise failed resolution.

**Minimum remedy:** classify an actual resolver failure/empty answer as UPSTREAM_UNAVAILABLE and close that OPEN connection; keep fail-closed policy for non-global/malformed DNS answers and genuine authority/control violations. One focused ordinary-DNS-failure recovery assertion suffices; no new resolver/supervisor/helper framework.

### R2-80-03 — LOW — ACK correlation uses Python coercive equality instead of strict wire types

**Source:** `api/src/omnis/supervisor/model_relay.py:99–125`; strict request counterparts `model_relay_protocol.py:18–20,122–124,135`.

The added ACK parser checks the exact key set, but validates version/sequence/scope only by `!=` against the request. Python `True == 1` and `False == 0`: an ACK with `version:true`, `sequence:true` for sequence 1, or boolean-valued generation/epochs inside an otherwise matching scope passes. `length` is correctly checked with `type(...) is int`; the correlated integer fields are not. This is a malformed-ACK acceptance bug, not evidence that the real broker currently emits such an ACK or an independent UID/TCB bypass.

**Minimal reproducer for parent:** in the existing ACK-double test, echo a correct FENCE or sequence-1 WRITE reply but replace version/sequence/nested epoch with bool. Current client accepts it; strict protocol should fail closed and retain uncertainty.

**Minimum remedy:** validate ACK version/sequence as actual bounded ints and parse/validate the echoed Scope before exact correlation. Extend the existing parser test, not the protocol surface.
