# Omnis reproducible delivery and operations

## When to Use
P0 and P8: dependency pinning, CI, containers, readiness, backup/restore, packaging and release decisions. Do not deploy or publish merely because the package builds.

## Prerequisites
Read stack baseline and rejected dependencies; inspect current manifests/locks and the exact phase acceptance gate. Use `terminal` for real system/git state. No install into the global Hermes environment to solve an application dependency problem.

## Procedure
1. Reproduce the relevant environment from exact locks in an isolated location. Keep Node, API, Hermes, proxy and browser executor environments distinct. Verify package registry metadata and immutable image identity when selecting a new pin; never silently replace the baseline with latest.
2. Audit the resolved dependency graph and licensing. A clean resolver/build is not a security approval. Record rejected versions, advisories and the remediation/retest gate. No forced resolver override or weaker TLS as a shortcut.
3. Add commands only for implemented components; CI uses the same commands, no real credentials, no live LLM, no external target traffic. Avoid network installations as a hidden step in lint/test. Mock protocol tests remain separately labeled.
4. For containers check actual listening interfaces, ports, volumes, UID, health, shutdown and egress topology. Do not expose Hermes/MCP/admin services publicly. Verify application dev instrumentation is absent from the production artifact.
5. Before migrations or storage changes describe backup consistency and recovery compatibility. Test restore into a fresh isolated instance, lease/capability revocation and stopped startup. Include encryption-key availability without copying secrets into Git.
6. At release require backend state, UI counts, reports and evidence hashes to match one immutable snapshot. Run documented gates, dependency audit and fault recovery; label unsupported auth/browser/provider paths rather than advertising them.
7. Review final history/status and changed artifacts. Push/deploy only if separately requested; then read the exact remote SHA/service state back. For failure, preserve diagnostics and execute the predeclared rollback, not an unreviewed downgrade.

## Pitfalls
Host Playwright/Chromium validation is not certification of the planned executor version. Docker tags can move. Git rollback does not restore DB or secrets. Documentation readiness is not runtime readiness.

- A wheel that imports its app factory may still omit migrations or process entrypoints. Build/install with dependencies exported/hash-checked from the lock in a fresh scratch venv, then migrate a disposable PostgreSQL DB **outside the checkout**. Exercise the installed supervisor, real Unix IPC and actual HTTP process, including restart and state readback; reserve the loopback listener rather than adopting whatever answers on a free-port guess. A Python audit guard needs a negative control and remains distinct from OS confinement. Source-tree/ASGI success or an archive filename check is not release evidence.
- Before rerunning an integration gate after a session handoff, verify required environment presence without printing values. Missing ephemeral test credentials are a failed prerequisite, not permission to read personal stores or weaken tests. Recreate a uniquely named disposable project when needed; keep setup/test/cleanup in one process if environment continuity is uncertain, and stop only resources whose ownership was verified.
- Bound trusted asset I/O as well as DB/control probes. Byte/hash limits do not bound filesystem latency; cancelling `to_thread` leaves its worker alive. Fault-inject repeated concurrent waits and cancellation, require one shared outstanding read per app, preserve API-ready versus assets-unavailable semantics, and verify a permanently stalled worker cannot hold interpreter exit.
- Assert that source tests import the current checkout, especially with worktrees and editable installs. Neutralize ambient Python/mypy paths and pytest selection/plugin settings in canonical commands; use explicit project config and isolated interpreters. Reproduce from a clean local-HEAD worktree with its own locked environment, not a shared editable package or an accidentally narrowed test selection.
- Pin and read back tool versions inside the actual foreground/background gate process, not only in an earlier shell. A login/background shell can restore an ambient Node even after a foreground PATH export; pass the exact toolchain PATH to the gate exec and preserve the failed preflight separately. Use a distinct short private TMPDIR for each concurrent non-OCI artifact build; still serialize all Docker gates and verify the exact prior family/fixture before the next one.
- The private PostgreSQL runner deliberately forwards only a small child environment (`PATH`, `HOME`, fixture bindings): outer `UV_PYTHON_INSTALL_DIR`, `UV_CACHE_DIR`, `PLAYWRIGHT_BROWSERS_PATH` and `XDG_CACHE_HOME` do not reach `make check-components`. After an ephemeral toolchain disappears, a fresh 0700 HOME needs explicit, verified access to the pinned managed Python under `$HOME/.local/share/uv/python` and the trusted pinned Chromium cache under `$HOME/.cache/ms-playwright`; private symlinks may point to those already-attested local artifacts without installing globally. First reproduce `uv venv --python 3.13.15` RED under the empty HOME and GREEN with the pin, then run `test-migrations` through the real runner on a new owned fixture and verify cleanup before repeating the full F gate. Keep TMPDIR short enough for Unix socket paths; do not weaken the runner's environment allowlist or report a targeted migration PASS as full `make check`.
- For an installed launcher gate, assert the CLI exit code separately from parsed JSON: shell pipelines can hide a failing producer. Make live integration tests depend on the current wheel build even with parallel Make; a previous scratch venv is not the artifact under review. Per-recv socket timeouts are not total IPC deadlines: use a monotonic budget across connect/send/read and prove it with a peer that trickles fragments.
- For OCI artifact probes, name and label every resource before launch, then in `finally` inspect and attempt all owned-container cleanup before image-tag cleanup, even if build/run times out or the driver exits early. `--rm` alone cannot clean a container whose CLI was killed. Read back exact absence; report uncertainty if Docker is unavailable mid-cleanup. Explicitly strip an inherited image-probe flag from ordinary release gates and enable it only in the requested image target. Test a second nonroot UID against bundled public assets, not only the image default UID.
- For an installed-image timeout, `subprocess.run` kills only its direct child; own a process group before launch and terminate/reap it before inspecting Docker. An absent tag after finite inspections does not prove the daemon-side build finished: retain the private intent, refuse automatic retry even while the tag is absent, and report manual recovery rather than PASS. Recheck the canonical Unix socket, daemon ID and random ownership labels around cleanup, but do not call distinct Docker CLI invocations an atomic identity binding; same-UID/root socket replacement is outside the declared local threat model. Exercise a TERM-resistant real descendant and a tag appearing after the first inspect as separate negative controls.
- For PostgreSQL 18 on a private host bind, test the image's actual UID transition: the `postgres` process must traverse `/var/lib/postgresql` after the root entrypoint re-execs. Keep the outer XDG state root 0700 and grant only traversal on its dedicated DB bind root (0711), with PGDATA itself owned/mode-locked by the image; do not chmod a shared ancestor. An internal-only Docker bridge may discard loopback port publication even when `HostConfig.PortBindings` looks correct. Docker Engine <28 can expose localhost-published ports to same-L2 peers: do not keep a front bridge/published port merely to make HTTP reachable. Use an owned private API UDS with a host-only loopback forwarder, then attest no Docker ports and the internal network membership at runtime; a LAN/egress negative probe remains separate. A daemon upgrade or firewall change requires a maintenance/rollback plan for unrelated containers. For long gate wrappers, own the full test process group on timeout and retain the exact disposable DB project/volume; killing only `make` can orphan pytest after teardown.
- Separate strict startup port ownership from post-stop listener readback on Linux. `SO_REUSEADDR=False` refuses a foreign socket bound without listening, but server-first TCP FIN can leave owned `TIME_WAIT` after process exit and make an immediate `bind()` cleanup probe falsely report a live server. Keep exclusive bind preflight before startup; after stop verify the exact owned process/resources exited and inspect local `/proc/net/tcp` **and** `tcp6` for `LISTEN` (`0A`) without contacting a potentially foreign service. Report absence of a listener, not immediate port availability; an unsafe/missing table is uncertainty, and same-port restart needs a finite wait/conflict policy. Reproduce active IPv4/IPv6 listeners and own `TIME_WAIT` before trusting cleanup.
- Do not call an asyncio-owned signal timer a hard process deadline: a blocked event loop never starts its countdown, and `asyncio.run()` may wait forever for cancellation-resistant lifespan tasks after the serving coroutine ends. For an installed control API, keep the shutdown owner outside that event loop, pin the child with Linux `pidfd` through reap (a numeric PID can be recycled), and if `pidfd_open` fails disable numeric signal forwarding **before** `waitpid` frees that PID; start a monotonic deadline at the first signal, then kill/reap only that child and report unreconciled exit 4. Exercise real subprocesses with a blocked loop, a leaked cancellation-resistant task and a signal injected after reap; also run the installed OCI entrypoint. Set Docker's API stop grace beyond the owner's full deadline and reap margin (15s for 10+2), then fault-inject a blocked event loop in the installed image: require the exact owned container's `ExitCode=4`, `OOMKilled=false` and explicit UDS recovery on restart. A successful Compose stop command alone is not DB quiescence.
- An in-process Python `fork()` owner cannot make `waitpid` and a stop-state read atomic with only `pthread_sigmask` on the main thread: an `at_fork` callback can create an unmasked thread and the Python handler can reclassify an already-reaped exit 3 as 4. For robust PID1, use a freshly exec'd stdlib-only owner, block stop signals before creating any worker/thread and consume them with `sigtimedwait`; gate an exec'd worker on a parent-owned anonymous pipe until its pidfd is pinned, and arm `PDEATHSIG` plus parent-ID recheck before importing the app. Treat this as a design to prove with real owner-death, stop timing and installed entrypoint tests, not as implemented behavior merely because a wheel contains the worker.
- Do not treat a shared pytest subreaper's post-baseline child list as proof of lineage: an unrelated child can arrive after the snapshot, and a grandchild may be adopted only after an initial cleanup pass. Prove owner-death in a dedicated supervisor process that creates no other children, drains adopted descendants in bounded rounds and reaps them before reporting; pin process identity before signaling, keep a parent-owned rescue path for fault-injected cleanup, and use total-deadline/byte-limited marker reads rather than `select` followed by unbounded `readline()`. If both signal and enumeration evidence fail, report uncertainty instead of claiming cleanup.
- For a long canonical test gate, establish family ownership in a fresh dedicated process before launching the command: a PGID alone misses setsid descendants already used by the suite. Pin direct adoptees with pidfds, reap already-dead adoptees while tests run without signaling live processes, then drain/rescan/reap late descendants before the private completion receipt. The parent starts with teardown disallowed before the gate call and permits DB teardown only after a verified family-drained return; signal errors must not bypass this rule. Keep observer-owned rescue and an unrelated late sibling in bounded regressions, not a growing product-owner harness.
- For a canonical PostgreSQL test gate on Docker Engine <28, a Unix Docker endpoint does not prove the daemon shares the runner's network namespace; `network_mode: host` grants host egress even if PostgreSQL binds `127.0.0.1`, and a matching volume name does not prove fresh disposable data. Prefer an internal/no-network PG18 container exposed to the host only through a private authenticated UDS bind; attest image/volume/socket provenance and permissions before any DDL and preserve the volume on owned teardown. Do not certify an intermediate WIP `make check` as safe while that fixture is unresolved.
- For an installed control-topology proof, compare the **complete** runtime mount set and security settings, not only an expected mount's presence: DB data writable plus its secret file read-only, API/supervisor exact private binds, mapped UID, read-only rootfs, dropped capabilities, no-new-privileges, internal network and zero Docker ports. Mutate each boundary in both the installed Compose contract and runtime inspect channel, then exercise actual installed containers; static config alone is not confinement. A forwarder exit between `poll()` and `killpg()` or a failed one-off `rm` must not skip other attested cleanup; attempt all owned teardown actions and report combined uncertainty instead of STOPPED, preserving DB data.
- A socket timeout is per `recv`, not a total HTTP response deadline. `http.client.HTTPResponse.begin()/read()` can be held indefinitely by a peer trickling headers/body; `makefile()` uses `recv_into`. Apply one monotonic remaining budget across connect/send/`recv`/`recv_into`, cap response bytes, refuse redirects and ambient proxies, and test real UDS and fixed-loopback trickle peers on the same evidence channel. The outer readiness loop is a separate budget, not a substitute for bounding one request.

- For installed startup, lock the installation/project as well as the state root: two XDG state roots can share one image receipt/project. Record a fresh attempt nonce before creation, bind services and network to it, and attest IDs/image/daemon/configuration/mounts/IPC together; use no-recreate, never a label or PID alone. Re-read daemon/family uncertainty immediately before DB teardown, including uncertainty raised by an earlier remove. Preserve forwarder handles on failed readiness and preserve exit 4 if the cleanup journal cannot be written.
- In an installed-command observer, persist a private recovery locator before launch and in an outer finally. Verify FAILED_CLEANED against exact absence before rescue; compare timestamps/restart counts, not only CIDs, on retry. Never rescue an unsettled daemon/writer outcome into a passing cleanup. Exercise a read-only startup phase for a clean SIGTERM proof; uncertainty controls remain explicitly distinct. Reclaim a fresh attempt's stale IPC only after settled container teardown, under the original service locks, with private inode/type/mode checks and a refused UDS connection; never delete lock files or signal their contents.
- For installed implicit `omnis`, test the real default port under a bounded exclusive-bind preflight; a random test port supplied only to later `start --port` commands manufactures a `PORT_CHANGE_REQUIRES_STOP` failure and does not exercise the default. In a private HOME browser fixture, set Playwright's pinned executable cache path explicitly while keeping profile and TMPDIR disposable. Pass pairing codes only through private PTY/stdin/body, never argv/env/reports; log a sanitized result and require an owned browser-close receipt before declaring cleanup. A completed OS opener request is not proof of a visible window.
- For read-only pair/open on an installed instance, preflight a strict existing startup receipt before acquiring lifecycle locks that create files, then compare the same receipt under those locks; missing/stale state must not leave new lock artifacts or open a foreign origin. In an installed observer, publish `VERIFIED` only after negative controls, browser-close and exact owned teardown/readback plus the final receipt; a positive mid-run flow marker is not a cleanup verdict.

## Verification

For startup error-path acceptance, load [startup failure boundaries](references/startup-failure-boundaries.md): distinguish signal/timeout/ordinary refusal and verify the installed JSON/exit contract on structurally hostile but byte-bounded input. These checks supplement the existing positive OCI proof, not replace it.

A clean checkout reproduces checks/build from locked inputs, deployment scope remains private, restoration has been exercised and every blocked gate is visible. Versioned instructions state what actually ran and how to undo external changes.
