# Omnis — arhitectura MVP, baseline API-key-only

**Baseline amendat HF01–HF10 · API/control/web P0.1–P0.3 implementate local; P0.4 în curs, G00 deschis; motor pentest neimplementat**

## 1. Autoritate și domeniu

Acest document este canonul de comportament API-key-only aprobat în T0. [Planul](Omnis_Implementation_Plan.md) decide ordinea/gates; [stackul](Omnis_Stack_Baseline.md) dependențele și limitele probelor; [UI/UX](Omnis_UI_UX_Spec.md) și [DESIGN.md](../DESIGN.md) interfața acceptată. §5/§8.1 definesc cele cinci contracte noi. §5.H și referințele explicit LEGACY_ONLY păstrează numai istoria Hermes. Reviewurile/probele din verification rămân scoped la snapshoturile lor, nu acceptare a runtime-ului nou. T0 nu implementează produsul.

**„Final” înseamnă o bază coerentă, versionată, de pornire, nu integrare deja validată.** P2/P3 au porți explicite de fezabilitate. Nu substituim o probă eșuată cu o promisiune sau cu o reducere tacită a MVP-ului.

### Inclus

- Linux x86_64, un operator local, un engagement activ; orchestrator și un slot de worker inițial, investigator apoi validator cu attempt/context separate; extinderea la doi workeri are gate propriu.
- Aplicații/laboratoare proprii, izolate și autorizate; HTTP(S), formulare, REST/JSON, SPA, JS static și import OpenAPI local revizionat.
- Recon anonim și autentificat opțional; hartă și matrice de coverage; Brain, investigatori, validator separat, delte, approvals, Stop, pause/resume și reconciliere.
- Trei familii demonstrate: control de acces la obiecte (IDOR/BOLA), XSS reflectat, traversal read-only către canary autorizat. Etichetele IDOR/BOLA nu dublează aceeași verificare.
- Settings OpenRouter/OrcaRouter API-key-only, default și model/conexiune per rol, Test model independent; catalog/editare/review/eval/publicare Skills; raport HTML/JSON și retest după M-LAB.
- Ambele moduri general/focalizat, campanie adaptivă G-LOOP, path bounded G-PATH și Jev integrat/evaluat în shadow; advisory numai calibrat. Research contextual și improvement editorial sunt auxiliare, nu înlocuitori ai pentestului.

**Prima felie:** un copil, recon minim → BOLA → validator independent → raport/retest (G05a/G06a). **MVP coerent:** trei familii într-o buclă adaptivă, browser, ambele moduri, Jev, path bounded, Settings și gates P0–P8. **Produs competitiv:** extinderi E1–E4 din plan; trei familii sau E1 nu înseamnă paritate Strix. Omnis este construit prin reutilizare efectivă de cod/teste/prompturi/metodologie OSS (stack §10), nu wrapper Strix sau rescriere a fundației.

### Exclus din MVP, nu plafon permanent al produsului

SaaS, acces public, multi-tenancy, colaborare, SSO/MFA autonom, un nou framework de agenți, marketplace/autoinstall Skills, graph DB, vector DB, Redis/Celery, Kubernetes, execuție shell generică, scanarea LAN-ului, SQLi general, stored/DOM XSS, SSRF/OAST, upload executabil, credential brute-force/încercări de parole și enumerare nelimitată, DoS și chains avansate (pathul bounded G-PATH este excepția adoptată). E1–E4 precizează promovarea subfamiliilor; SaaS/multi-tenancy și alt deployment cer decizie separată. Observarea unei suprafețe nesuportate nu o transformă în test executat.

## 3. Procese, rețele și granițe de încredere

```text
Browser operator → loopback Omnis web/API → PostgreSQL + artefacte + seif
                                   ↓ comenzi durabile
                         supervisor Omnis (unic)
                           ├─ Settings/operații sistem → seif + sender provider
                           ├─ Agent/Runner → dispatch Omnis → OpenRouter/OrcaRouter
                           └─ tool broker → HTTP trusted / sandbox / Chromium
                                               ↓ transport autorizant și capture
                                          laborator/țintă în scope
```

Separăm procesele pentru ciclul de viață și autoritate, nu pentru scalare distribuită. Un singur repo, un singur model de domeniu și o singură DB Omnis. State DB Hermes este istoric de runtime, nu DB alternativă de produs.

**Baza de încredere:** launcherul, supervisorul, seiful, senderul provider, brokerul și adaptoarele fixate. Modelul, skillurile importate și outputul target sunt date neîncrezătoare. Agent/Runner este mecanică, nu autoritate de securitate. Scripturile generate rulează numai în sandboxul executorului, nu în API/supervisor; root sau același UID malițios rămân în afara garanției de izolare a aplicației.

### Topologie aleasă

- `control`: API, supervisor și DB; UDS privat și web numai loopback, fără port Docker/LAN public. Numai supervisorul are canalul provider dedicat; DB/API nu capătă egress general. Referințele P0/P1 sunt probe istorice, nu verdict pentru noul release.
- Execuția modelului este owned de supervisor, cu unelte Omnis strict înregistrate; nici tool SQL/admin generic, nici acces direct la host/seif/metadata. Un worker cu SANDBOX_EXEC (§9.6) primește workspace și tooluri în namespace separat, nu drepturile procesului de control.
- `executor`: HTTP trusted A05 verifică fiecare request la sink; shell/scanner/browser au egress exclusiv prin transportul autorizant certificat pentru ele. Fără fallback direct, DNS/UDP/QUIC necontrolat, host networking, Docker socket sau mount de repo/home. Identitatea invocării este atașată de Omnis, necunoscută modelului.
- `target`: numai senderul HTTP trusted sau proxyul/executorul admis poate ajunge la fixture. Fixture-ul nu accesează control plane/internet/rețeaua personală; evaluatorul deține truth/reset/canary separat. Email/plăți/webhookuri folosesc sinks autorizate.
- Provider egress (inclusiv Jev), target egress și **research egress** sunt trasee distincte. Research folosește adaptor/proxy de surse publice allowlisted, query minimizat, DNS/redirect/bytes/time caps și failover explicit; fără relay către țintă/control/host/metadata. Downloads sunt quarantine și nu execută PoC. Rețeaua refuză bypassul, nu doar un test pe hostname.

Rețelele bridge Docker au propriile reguli; `internal: true` singur nu certifică izolarea sau accesul la host.[6] G-NET cere refuzuri măsurate din namespace-urile afectate, inclusiv host gateway/IPv6, înaintea efectului. Refolosirea transportului privat nu transferă automat probele OAuth istorice către noul sender.

### Browser și HTTPS: alegere concretă

Pentru browser/scannere care cer proxy L7 folosim Playwright în executor și adaptor mitmdump, condiționat de G-DEPENDENCIES. **Buildul publicat `mitmproxy==12.2.3` rămâne respins pentru trafic target**; B01e-build/B01e-integrated îl remediază/verifică înaintea acestor consumeri. Primul API HTTPX trusted A05 nu depinde de acest proxy respins: vede L7 înainte de TLS și aplică aceeași policy/captură/Stop la sink, cu propriul G-NET. Excepția nu se extinde la shell/browser/scannere prin variabile proxy sau prompt.

- Proxy explicit; fiecare CONNECT este verificat la host/port **înaintea conectării upstream**, apoi TLS este interceptat pentru control per request.
- CA efemeră de laborator, instalată numai în containerul/contextul executorului; niciodată în trust store-ul operatorului. Cheia CA nu ajunge la model, worker shell sau țintă. Validarea certificatului upstream rămâne activă; CA proprie a fixture-ului este admisă explicit. Pinning/mTLS nesuportat produce `UNSUPPORTED`, nu `ignore_https_errors` global.
- Addonul implementează guard de conexiune, `requestheaders` pentru limite/refuz precoce și `request` pentru cererea completă; **request streaming oprit**. Documentația mitmproxy spune că, dacă streamingul este activ, evenimentul `request` poate veni după ce bodyul a fost transmis.[11]
- Configurăm explicit `connection_strategy=lazy`, fără certificate sniffing upstream înaintea autorizării, fără passthrough prin `ignore_hosts`/`tcp_hosts`, raw TCP sau upgrade WebSocket. Numele/opțiunile efective se verifică pe pin; valorile implicite nu sunt contractul Omnis.[10][12]
- HTTP/1.1 este transportul certificat MVP; HTTP/2, HTTP/3/QUIC, WebSocket, gRPC și protocoale raw nu sunt certificate. Nu facem request smuggling sau teste dependente de fidelitate wire-level prin acest proxy. Cererea observată de target este dovada efectului; versiunea originală a cererii și transformările proxyului se păstrează când sunt relevante.
- Guardul verifică URL brut, authority/Host/SNI/port, redirect și adresa rezolvată la conectare. Blocăm userinfo, scheme nepermise, ambiguități de parsare, metadata, loopback/link-local și adrese private din afara fixture-ului explicit. Nu blocăm generic orice RFC1918 și apoi exceptăm tot LAN-ul: laboratorul are adresare precisă.
- Conexiunile reutilizate nu ocolesc verificarea pe fiecare request. Rebinding, host/authority discrepant, redirect cross-origin și URL cu encodări ambigue au teste de refuz. Auth și cookies nu urmează redirecturi către altă origine prin copiere automată.
- Chromium: non-root, sandbox activ, seccomp compatibil, capabilități eliminate, fără `--no-sandbox`, fără `--ipc=host`, cu `/dev/shm` dimensionat privat. Imaginea Playwright documentată nu este declarată de producător drept sandbox suficient pentru site-uri neîncrezătoare; avem nevoie de hardening și probă proprie.[5]
- Service Workers se blochează; downloads/popups se blochează implicit, WebRTC/UDP și extensii sunt dezactivate. Un popup necesar unui login se permite numai într-o fereastră asistată explicită, pe originile de dependență aprobate. CSP a țintei nu este dezactivată pentru a fabrica XSS.

**Guardul real este proxy + rețea + broker.** Eroare addon, indisponibilitate policy/DB, lease expirat sau corelare lipsă înseamnă refuz, nu trafic permis. Cazul „addonul nu s-a încărcat” se verifică prin readiness și izolare: executori neporniți până la self-test negativ; un mitmdump generic fără policy nu este un serviciu acceptat.

**Binding browser→proxy:** un context/generație de browser aparține unui singur attempt pe durata lui, nu este transferat de la investigator la validator. `parent_action` reprezintă un workflow browser bounded (navigare și pași tipizați), nu fiecare click; pașii și requesturile au ID-uri proprii sub același părinte și nu extind permisiunea workflowului. Executorul de încredere deschide un `BrowserActionWindow` cu `(run, attempt, parent_action, auth_epoch, fencing_epoch, context_generation, deadline)` și canal proxy autentificat; metadata nu este pusă în headere ce ajung la țintă sau în argumentele LLM. Proxyul atribuie fiecărui request copil propriul action ID în acea fereastră și îl admite separat. Nu există două ferestre concurente pe același context. După închidere, fetchuri/timere de fundal se refuză; înaintea următoarei acțiuni se drenează și închide generația. Pentru MVP, contextul se reface dintr-un checkpoint de auth permis, nu se atribuie după timestamp o cerere întârziată unei acțiuni noi. Pierderea stării SPA/tokenurilor neregenerabile produce blocaj asistat, nu o excepție de policy. P3b probează cererea întârziată din generația veche exact când începe următoarea acțiune. Identitatea transportului singură nu este suficientă.

## 4. Control plane local și configurare

Loopback nu este autentificare. Omnis pornește numai pe `127.0.0.1`, cu Host allowlist exactă și același origin pentru buildul web și API. Dev Vite are host strict și proxy `/api`; nu CORS `*` sau porturi ascultate public.

`127.0.0.1` este bindul **forwarderului host**, nu un port publicat de Docker. Amendamentul P0.4 păstrează API UDS privat/peer UID și forwarder host; înlocuiește schița veche cu publicare Compose loopback. DB/IPC/runtime nu capătă port public. Health-ul intern folosește Host-ul configurat, fără a lărgi allowlistul sau a accepta X-Forwarded-Host arbitrar. G00 al profilului **strict local, un singur operator** cere atestarea reală a bindului loopback, UDS/permisiunilor, topologiei și absenței porturilor Docker; negativul fizic dintr-un peer separat LAN IPv4/IPv6 ori sub alt UID este amânat explicit la poarta existentă G-OPS/G-NET **înainte ca serviciul să fie accesibil altor hosturi sau utilizatori (LAN/remote/public, bind non-loopback, multi-user)**, cu status `NEED_TO_TEST_PUBLIC_EXPOSURE`, nu PASS. Uvicorn TCP direct este numai exemplu de dezvoltare.

**Bootstrap ales:** launcherul generează un cod local de pairing, unic/expirabil, afișat numai operatorului în terminal; formularul local îl schimbă o singură dată pe o sesiune opacă server-side. Codul nu apare în URL, Git sau log de request. Rată limitată, verificare Host/Origin și timeout. Cookie `HttpOnly; SameSite=Strict; Path=/`, fără `Domain`; HTTP loopback este limita asumată, nu pretindem TLS. Mutările cer și token CSRF legat de sesiune; SSE cere aceeași sesiune. Logout invalidează server-side; expirarea sesiunii UI nu anulează automat engagementul, dar nu permite control neautorizat. Refuzăm extinderea bindului; accesul remote ar cere TLS și alt threat model.

Un proces malițios cu același UID/root pe host rămâne în afara garanției. Nu prezentăm seiful, cookieul sau containerele drept protecție față de administratorul hostului.

Paths propuse pentru instalare, nu create acum: `$XDG_STATE_HOME/omnis` (implicit `~/.local/state/omnis`), runtime homes sub acest root, **nu sub `~/.hermes`**, configurație non-secretă sub `$XDG_CONFIG_HOME/omnis`, secrets cu permisiuni restrictive. Nu montăm `/home/kali`, checkoutul personal Hermes sau `.codex`. State/secrets/evidence/backups nu trăiesc în repo.

Settings are un singur owner de mutații. Editarea configurației pentru runuri viitoare și a drafturilor inerte rămâne permisă; snapshotul runului activ nu se schimbă. Înlocuirea/revocarea credentialului oprește/drenează utilizările afectate (§8.1), fără hot-swap. Nu există management Hermes, reveal, filesystem/env admin generic sau validare online la Save.

### 4.1. Experiența instalată: `omnis`

**Contract MVP parțial implementat:** SL02 livrează `omnis start --no-open` și statusul HTTP/assets/control din artefactul instalat ([dovezi și limite](verification/p04-installed-start.md)); SL03 livrează `omnis pair`, `omnis open` și `omnis` implicit cu cod inițial numai pe TTY la instanță nouă, origin verificat și opener raportat onest ([dovezi și limite](verification/p04-pair-open.md)). Stop/recovery rămâne SL04. **Comportamentul complet propus:** După instalarea explicită a releaseului local, operatorul execută **`omnis`** din orice director: serviciile pornesc în fundal, iar browserul implicit deschide Omnis când dashboardul este ready. La prima utilizare, pagina cere pairingul local de mai sus; nu intră neautentificat în datele engagementului. Cu sesiune validă, ajunge direct la dashboard. Acceptarea comenzii OS de deschidere nu dovedește singură fereastra sau sesiunea. Nu pornește TUI-ul sau dashboardul administrativ Hermes.

`cli/` livrează un console script executabil `omnis` dintr-un wheel Python, cu mediu mic separat. Nu impunem un binar monolitic PyInstaller/Electron și nu pretindem că PostgreSQL/Chromium/executorii sunt încorporate în acel fișier. Releaseul conține launcher, manifest/checksums, configurațiile Compose și imagini OCI fixate; buildul web este inclus în imaginea API, nu servit de Vite în utilizarea normală. Instalarea/pullul inițial și upgradeul sunt operații explicite, nu efecte ascunse ale startupului.

| Comandă propusă | Contract pentru operator |
|---|---|
| `omnis` | Start idempotent + așteptare readiness + deschidere browser |
| `omnis start --no-open` | Același startup, fără GUI; pentru headless/CI |
| `omnis open` | Deschide numai o instanță verificată deja pornită; nu pornește un run |
| `omnis status` / `omnis status --json` | Stare servicii, instance/release/schema, readiness separat; output sanitizat |
| `omnis pair` | Emite un nou cod local one-use/expirabil numai într-un terminal interactiv; nimic secret în JSON/argv/URL |
| `omnis run stop` | Oprește runul activ identificat explicit în comandă/output, fără confirmare; dashboardul rămâne pornit |
| `omnis stop` | Cere Stop/revocare/drenare, apoi oprește instanța și serviciile proprii; păstrează volumele/datele |
| `omnis doctor` | Diagnostic local sanitizat; nu face inferență, login, target probe sau reparare distructivă automată |

La rezolvarea runului activ, clientul de control leagă comanda de ID/revizie; dacă între timp contextul s-a schimbat, raportează conflict, nu oprește un alt run printr-o selecție implicită stale. Closing browser/terminal nu oprește serviciile detached. Nu instalăm implicit serviciu de boot al OS-ului; după reboot pornirea rămâne explicită și fără autoresume de assessment.

### 4.2. Startup determinist, independent de cwd

**Profile de livrare, nu stări simulate:** fundația P0/P1 păstrată pornește DB/API/supervisor/web inert, fără provider IO. T1 adaugă seif/Settings/ModelTest, T2 biblioteca și rol/task/tool loop, T3 execuție/evidence/auth. SSE se certifică la consumerul B08, nu dintr-un flag READY. Capabilitate nelivrată → UNAVAILABLE, nu activare simulată.

**Inert înseamnă zero apeluri provider**, nu numai zero inferențe: fără validate, model discovery/pricing, refresh OAuth, login sau verificare online implicită la boot/status/health/open. Configurația/statusul local pot fi citite numai prin DTO-uri fără secrete; probele online Settings cer o acțiune/acord separate. Instalarea/pullul explicit sunt în afara startupului și nu îi dau dreptul să contacteze providerul sau ținta.

Owner: `cli/src/omnis_cli/instance.py` și `compose.py` pentru instanță; supervisorul este singurul owner al runului. Launcherul folosește căi absolute din manifestul releaseului, argv ca listă și environment allowlisted; nu citește `.env`, Compose overrides sau scripturi din cwd. Nu schimbă profilul Hermes personal.

1. Validează OS/distribuția, release/checksums, Docker/Compose disponibile, configurația non-secretă și permisiunile directoarelor. Regulile de host care cer privilegii se pregătesc prin instalare explicită; launcherul verifică precondițiile, fără sudo sau modificare globală de firewall pe ascuns. Nicio instalare, descărcare sau migrare de upgrade implicită. Release lipsă/incompatibil → eroare acționabilă.
2. Ia lock exclusiv local per instanță și verifică identitatea Compose/manifestului. Dublu launch reutilizează aceeași instanță; un PID sau un port care răspunde nu dovedește ownership. Numele proiectului/etichetele nu se deduc din cwd.
3. Port propus implicit **`127.0.0.1:8765`**, configurabil explicit numai cu serviciile oprite. Host/Origin allowlist urmează exact originul configurat. Port ocupat de alt proces → conflict, fără kill, auto-port sau deschidere a paginii străine. Pentru o instanță existentă verifică identitatea/readiness prin canalul local autentificat și originul HTTP asociat; dacă este sănătoasă, trece la deschiderea UI fără migrare/restart sau schimbarea writerilor. Pentru o instanță nouă continuă cu pasul 4; readiness HTTP se verifică după startup. Alt release/instance ID → refuz.
4. Pornește DB și așteaptă health bounded. Rulează jobul de migrare **o singură dată**, cu lock DB și verificarea schemei; la instalare nouă creează schema din release. La date existente, versiune incompatibilă/upgrade necesar → oprește startupul și cere procedura explicită de update/backup, nu migrează distructiv pe ascuns.
5. Pornește API-ul și supervisorul unic; adaptorul runtime inert se pornește numai dacă profilul P2 instalat/admis îl include. Absența lui în P0-control este UNAVAILABLE, nu healthy și nu blocaj al bootstrapului web. API servește numai assets trusted ale buildului și `/api` same-origin. Supervisorul dobândește ownership/lease DB, verifică inboxul și intenția durabilă de shutdown a instanței, marchează runurile întrerupte pentru reconciliere și nu reia prompturi/efecte. Admiterea rămâne închisă cât un shutdown este incomplet; operatorul finalizează `omnis stop`, apoi cere o nouă pornire. După oprire completă/instalare nouă, startupul explicit poate redeschide admiterea într-o generație nouă, numai după verificarea stării. Restart/reload API nu redeschide admiterea și nu creează al doilea supervisor.
6. Provisionarea normală a serviciilor de execuție rămâne ordonată: numai B01e-build plus B01e-integrated/G-NET pentru transportul cerut, reguli de rețea aplicate și self-test negativ al addonului permit containerele worker HTTP/browser. Certificarea se construiește înainte într-un harness separat, izolat și autorizat; nu prin activarea prematură a assessmentului. Niciun browser context, sesiune Brain sau request target nu se creează la boot. Proxyul refuză tot fără run/lease. Dacă aceste gates nu sunt disponibile, pornește **numai control plane-ul**, cu Start blocat și motiv vizibil; nu rulează proxyul respins pentru a obține un dashboard „verde”.
7. `DASHBOARD_READY` cere DB/schemă/assets/API/control sănătoase. `ASSESSMENT_READY` este separat și cere runtime/provider/policy/confinare/buget la preflight. Lipsa contului sau proxyului certificat nu împiedică folosirea drafturilor/Settings. Health nu apelează modelul sau ținta. Frontendul afișează gate-ul lipsă, nu cost zero sau zero findings înaintea răspunsului.
8. Launcherul generează codul de pairing local și înregistrează digestul/expirarea prin canalul local autentificat; valoarea se afișează numai pe TTY, nu în logs sau output JSON/redirecționat. Consumul atomic este al serviciului de sesiuni, nu al UI. În headless, pairingul este o acțiune ulterioară explicită. Deschide originul configurat (implicit `http://127.0.0.1:8765/`) numai după readiness; fără cod în query/fragment. Browser indisponibil → serviciile rămân ready, URL și instrucțiune de deschidere manuală, fără succes GUI inventat.

Bugetele startup/shutdown sunt finite și configurate, nu bucle infinite. Cod de ieșire propus: `0` pentru operația de lifecycle verificată (dashboard ready nu înseamnă assessment ready), `2` config/precondiție/port incompatibil, `3` startup/readiness eșuat, `4` stop/efecte nereconciliate. JSON include explicit `dashboard_ready`, `assessment_ready`, `browser_opened` și motivul degradării, niciodată coduri/secrete.

**LEGACY_ONLY — bugetul de pornire nativă P2:** limita de 10 secunde și probele vechi rămân în [registrul istoric](verification/p4a-minim.md). Nu este deadline sau prerechizit de startup pentru noul runtime; T1 păstrează deadline-ul propriei operații (§5).

Eșec parțial: consemnează serviciile proprii pornite în această încercare și oprește numai acele resurse când nu există instanță preexistentă sănătoasă. Nu șterge volume sau date, nu oprește alte proiecte Docker și nu resetează DB. Un crash al launcherului lasă cel mult servicii fără lucru autorizat; următoarea pornire reconciliază identitatea/starea, nu lansează încă o copie.

### 4.3. Owner, canale private și oprire

Supervisorul deține execuția SDK, taskurile, DB și schedulingul; executorii dețin numai invocările tipizate și process groups sandboxate. Canalele Unix private verifică peer/owner/mode și generația/epochul, limitele de mesaje/backpressure/deadline. Nu există proces Hermes sau queue durabilă alternativă în noul runtime. Outputul toolului este dată, nu autoritate. EOF/ACK pierdut cere reconciliere, nu retry de efect.

- Provider egress separat, finit și revocabil, fără rețea generală pentru control plane. Schema/senderul trusted verifică requestul înainte de TLS; conexiunile reutilizate nu ocolesc Stop.
- Watchdog/lease pe executori: pierderea ownerului sau DB închide admiterea și drenează/oprește bounded procesele proprii, inclusiv descendenții. Refuzul toolurilor nu dovedește anularea inferenței remote. Rezultatele vechi pot fi primite receive-only, nu autorizează continuare.
- Settings/seif este owned de supervisor; nu există proxy administrativ către Hermes sau alt motor.
- **IPC operator ↔ control plane:** socket local separat `control.sock`, disponibil launcherului host și componentei de control, nu runtime-ului. `api/src/omnis/transport/local_control.py` autentifică owner/peer și capability locală; permite doar status/pairing/stop și tranziția tipizată de admitere a instanței după startup/reconciliere. Acest canal nu ocolește autoritatea DB, nu devine HTTP admin fără sesiune și nu împrumută credentialul providerului. UID mapping și permisiunile socketurilor sunt probe P0/P2, nu presupuneri bazate numai pe un volum.
- **Un singur client de container lifecycle:** launcherul host are accesul operatorului la Compose. Nici API, supervisor, runtime, executori, proxy sau tool model-facing nu primesc Docker socket, privileged mode sau generic exec. Serviciile fixe sunt provisionate de launcher în ordinea §4.2; supervisorul activează doar procese/contexte tipizate din containere deja admise. Dacă lipsește serviciul, Start este blocat, nu provisionat printr-un escape hatch.

`omnis run stop` și butonul Stop folosesc aceeași comandă durabilă/idempotentă: revoke/fence → închidere admitere pentru run → întrerupere/drenare runtime/executori → readback. `STOPPING` rămâne până la dovada quiescenței; bytes deja trimiși pot rămâne UNKNOWN.

**Oprirea instanței are o barieră suplimentară, înainte de Stop run.** Toate comenzile CLI care schimbă lifecycle-ul instanței folosesc același lock local. `omnis stop` persistă tranzacțional în `InstanceControl` intenția de shutdown, `admission_open=false`, un `shutdown_command_id` idempotent și o generație monotonă. Start/Resume, launch/continuare model, writer Settings și fiecare admitere de task/acțiune verifică această barieră sub același lock DB/tranzacție; nu este o bifă în UI. Astfel, un Start concurent fie este admis înaintea închiderii și inclus în oprire, fie este refuzat cu `INSTANCE_SHUTTING_DOWN` — niciodată admis între quiescență și oprirea containerelor. Stop și citirile de diagnostic rămân permise.

Cu admiterea instanței închisă, supervisorul oprește runul și writerii prin adaptoarele tipizate, persistă dovada de quiescență/generație, apoi launcherul oprește numai containerele proprii, cu deadline și fără `down -v`/ștergere de date. API și DB rămân disponibile până la persistarea rezultatului. Crashul launcherului nu șterge intenția din DB și nu redeschide admiterea; noul proces continuă shutdownul idempotent. Receiptul local de containere oprite nu rescrie singur stările de run/effect din DB. O nouă pornire explicită verifică finalizarea și generația înainte de redeschidere; un run nereconciliat rămâne blocat separat de disponibilitatea dashboardului.

Dacă API/supervisor nu mai răspund, launcherul poate opri numai containerele identificate din manifest/etichete/ID-uri proprii, inclusiv runtime, executori și proxy, pentru a elimina căile de efect. Raportează **oprire de urgență / stare nereconciliată**, nu inventează `STOPPED` în DB. La restart, runul intră în NEEDS_RECONCILIATION; nu autoresume și nu retry al acțiunilor UNKNOWN. Nu folosim `pkill`, kill după port sau curățare globală Docker.

**Contract aprobat pentru remedierea SL04, încă neimplementat/probat: owner host dedicat exclusiv Stop.** După commitul barierei DB, quiescență și FINALIZE, dar înaintea primului efect host, launcherul persistă/citește înapoi intenția cu command ID, generație/epoch, identitatea daemonului și inventarul exact al resurselor proprii. Transferă exclusivitatea acelorași lockuri locale și handle-urile de ownership unui proces host cu entrypoint fix, scop limitat la această comandă Stop; numai acesta execută stop/rm/cleanup, cu argv și mediu allowlisted, fără API generic, Docker socket în servicii, runtime Hermes sau promovarea ownerului exec WIP. Un handshake verificat precede cedarea autorității de către CLI; moartea CLI-ului nu eliberează lockul și nu abandonează efectul deja admis. Ownerul păstrează per-etapă `PREPARED` fsynced înainte de efect, dovada ACK-ului/daemonului și a familiei CLI/drainului exact înainte de `COMPLETED` fsynced, apoi readbackul resurselor; numai receiptul complet verificat permite `STOPPED`/exit 0. Un ACK pierdut, timeout, owner mort, daemon încă activ ori familie neidentificată rămâne `UNCERTAIN`/`RECOVERY_REQUIRED`; un CID absent nu înlocuiește receiptul și retry-ul nu pretinde că a văzut ACK-ul procesului mort. Ownerul nu devine serviciu persistent de boot sau supervisor generic, nu primește autoritate asupra altor proiecte și nu pornește efecte după invalidarea identității/lease-ului. Acest contract are nevoie de teste RED, probe reale de parent-death, child/reap/daemon și cut-uri instalate pe fixture propriu, plus review independent înainte de implementare acceptată; textul nu certifică ownerul existent.

**Politică SL04 de fence durabil, confirmată de operator:** un `SELECT` al lease-ului supervisorului înainte de Docker nu poate revoca o cerere deja acceptată de daemon. După FINALIZE și înainte de primul efect host, o tranzacție pe `InstanceControl` și `supervisor_lease` verifică ownerul/epochul curent și armează o autoritate Stop **unică**, legată de command ID, generație, epoch, identitatea daemonului și inventarul propriu. Commitul acestui `STOP_PENDING` este frontiera DB; `acquire` și `open` refuză atât `STOP_PENDING`, cât și `STOP_UNCERTAIN` chiar dacă lease-ul supervisorului expiră sau este eliberat. Grantul Stop este distinct de heartbeatul de cinci secunde și nu expiră automat: ownerul are un buget finit pentru fiecare efect, însă o cerere Docker deja admisă poate ajunge la daemon după moartea clientului. Când ACK-ul ori receiptul lipsește, blocajul persistă fără retry distructiv și fără takeover/Start; numai reconcilierea externă verificată îl poate dezarma. După Stop complet, DB poate rămâne indisponibilă cu fence-ul încă armat; un **Start nou și explicit** verifică local receipturile fsynced, daemonul, CID-urile absente și PGDATA originală, repornește numai DB-ul atestat, reconciliază tranzacțional fence-ul **înainte** de achiziția noului owner/supervisor și OPEN, apoi continuă pornirea. Un receipt local sau simpla absență a CID-ului nu dezarmează singure DB-ul; pierderea ACK-ului de reconciliere este refuz idempotent, nu autoresume. Nu există timeout de deblocare, migrare retroactivă a receipturilor legacy, acces Docker în servicii sau promisiune că un efect deja acceptat poate fi anulat. Această politică este un contract de implementat și probat pe PostgreSQL/CLI instalat, nu un PASS pentru ownerul sau gate-urile actuale.

## 5. Runtime API-key-only și autoritatea execuției

**Contract aprobat în T0; implementare T1/T2, nu runtime acceptat.** OpenRouter/OrcaRouter prin API keys; `openai-agents` este biblioteca candidată Agent/Runner/tool loop, distinctă de clientul `openai`, fără obligația unui cont OpenAI. Nu există Hermes runtime sau Codex subscription/OAuth în noua execuție. Biblioteca nu deține autorizația, persistența canonică ori verdictul de securitate. API-ul web nu pornește scheduler în request/lifespan; supervisorul existent este unicul owner.

**Producer → primul consumer:** click explicit Settings/Test model → API autentificat și same-origin/CSRF → canal privat tipizat → supervisorul admite și persistă `SystemOperationV1` → transportul modelului consumă `ModelDispatchV2` (§5.2). Fără engagement, MissionSpec, Publish, catalog ori pregătire nativă. T2 folosește același sender pentru fiecare apel al Runnerului, nu un smoke cu infrastructură abandonată. Save/read/boot au zero apeluri provider.

**Persistență aleasă:** tabelă `system_operation` aditivă, cu coloane tipizate, UNIQUE(instance_id, command_id), stări finite, refs către snapshot/input/outcome deținute și receipturi de comandă. Dispatch/observații v2 sunt persistate separat de ledgerul V1, în același PostgreSQL/owner, nu în `catalog_command` și nu un managed-run fictiv. Migrații noi după 0013, fără rescrierea 0001–0013. Un Ref se rezolvă după kind/id/revision/digest și ownerul stabil al instanței; hash-ul unui obiect trimis de client nu dovedește că producerul legitim l-a emis. Rootul RUN devine disponibil numai cu producerul autentic T2; T1 nu acceptă acel context printr-un enum fără consumer.

**Idempotency:** aceeași comandă și cerere canonică → aceeași operație/readback; payload diferit → 409. Rejucarea citește snapshotul original înaintea verificării configurației *curente*, fără readmitere. O comandă nouă cu expected revision stale este refuzată. Cancel are command ID propriu și expected state revision, fără a șterge Start. Citirile terminale/replay sunt receive-only inclusiv după Stop. Autoritatea procesului (owner/epoch/generation) este distinctă de identitatea stabilă a operației.

**Stări și reconciliere:** PENDING → RUNNING → FINISHED; Cancel/Stop → STOPPING până la quiescență locală demonstrată, apoi FINISHED/CANCELLED. FINISHED nu implică succes provider sau usage complet. La owner-loss/crash fără dovadă locală: NEEDS_RECONCILIATION. Restartul nu reexecută PENDING/SENT și nu face autoresume. Ownerul nou poate doar reconcilia/citi rezultatele înaintea unei comenzi noi; netrimis demonstrat permite eliberare, posibil trimis păstrează UNKNOWN. După reconcilierea locală este permis un test nou explicit chiar dacă outcome-ul remote rămâne UNKNOWN; istoricul/consumul incert rămân, fără rambursare fictivă. Nu este exactly-once upstream.

**Serializare comună:** InstanceControl → lease/fence → conexiune → operație → ledger → dispatch; la run, scope-ul runului ocupă locul operației. Requested nu se copiază în observed; un parametru neverificat rămâne neconfirmat și nu satisface REQUIRED. HTTP 200 cu error/mid-stream error nu devine succes. Pentru Test model succesul cere răspuns complet conform contractului sintetic; nu certifică pentest. Outputul parțial se păstrează etichetat; instrucțiuni/tool arguments incomplete nu se execută. Provider completed cu output local TRUNCATED rămân două fapte distincte. Late receipt după Stop completează istoricul, fără wake/continuare nouă.

`cost_observed` și `cost_estimate` **nu se adună** pentru același apel; subtotalul cunoscut este etichetat incomplet când există cost UNKNOWN. Receipt duplicat nu dublează counters, iar eșecul poate consuma. API întoarce 202 numai după admitere durabilă, GET după operation ID este receive-only, 409 la command/revision conflict; Cancel are readback. Ruta existentă `/api/v1/model-test` este adaptată cu readback pe ID și Cancel, fără producer nativ; nu se publică endpointuri/stuburi înaintea consumerului. DTO/OpenAPI/decoderii manuali TS/UI se schimbă împreună în T1; SDK-ul nu este accesat din browser.

### 5.5. Distribuție și compatibilitate

Release API-key-only cu identitate/manifest/schema/closure proprii, pinuri admise și zero instalare/upgrade/provider IO la boot. Prima migrare se verifică într-o **instanță separată**; nu adoptă automat PGDATA/profiluri/grants/operator releases. Upgrade în loc ulterior cere backup/restaurare probate; Git revert nu restaurează DB/secrete. API și DB rămân pe rețeaua control internă; numai senderul trusted al supervisorului accesează canalul provider dedicat. Relay-ul host existent se adaptează finit pentru endpointurile routerilor, fără proxy arbitrar, acces general la internet sau reutilizarea sa ca broker target. Cheia master se montează numai ownerului seifului; executorii sandbox nu primesc DB/seif/chei AI/Docker socket.

Istoric de suportat prin readeri **receive-only**: drafturi/revizii; catalog/provenance/publication receipts; task/attempt/result/check/qualification/inbox și ledger/ModelTest V1 persistate. Fiecare categorie declarată supported are fixture/producer/revizie și probă pe noul artefact **fără reluarea** Hermes, recompunere executabilă, model sau target. 0001–0013/date/licențe/notices și identitățile istorice se păstrează. Categoriile încă neprobate sunt NOT_RUN/indisponibile explicit și datele rămân arhivate; nu compatibility PASS și nu migrare semantică retroactivă.

## 6. Scheduler, taskuri, continuări și bugete

Supervisorul unic deține dispatcherul, runtime-ul și lease-urile. API poate avea mai multe procese în viitor, dar nu pornește schedulerul în lifespan. PostgreSQL oferă advisory locks la nivel de sesiune sau tranzacție; alegerea și eliberarea lor trebuie să fie explicite.[8]

- Lease de supervisor și `fencing_epoch` persistent; un singur engagement activ prin constrângere DB/lock. Workerul care pierde lease-ul nu mai poate admite/expedia acțiuni.
- Joburi/taskuri în PostgreSQL, claim tranzacțional cu `FOR UPDATE SKIP LOCKED`; fencing token la execuție. Nu ținem tranzacția deschisă în timp ce așteptăm rețea, LLM sau operator.
- DB state + domain event în aceeași tranzacție. Cursorul per engagement se alocă prin incrementul unui counter row blocat până la commit; un BIGSERIAL global singur nu ordonează commiturile și nu este suficient pentru SSE. Inbox de delte și marker de consum durabile. Completion-ul workerului intră în inboxul Omnis; numai ownerul consumă o dată delta și admite continuarea, fără wake paralel al SDK-ului.
- `delivered`, `admitted`, `turn_completed` și `domain_result_consumed` sunt stări distincte. ACK de transport/SDK nu dovedește ultimele două. După crash reconciliem task/result IDs și cursori; rezultat neconsumat se livrează din nou numai după verificarea proprietarului turului. Consum idempotent, nu promisiune de exactly-once pe rețea.
- Un dispatch cu răspuns pierdut nu se retrimite orb; attempt durabil, receipt/readback și reconciliere înainte de decizie. Incertitudinea poate bloca automatizarea până la operator.
- Cozi separate conceptual pentru investigație/validare; rezervă de trafic/timp pentru validare, fără rezervă „de prompt” care poate fi consumată tacit de recon.

### State machines normative

`EngagementRun`: `PREFLIGHT → READY → RUNNING → PAUSING → PAUSED/HOLD → RUNNING`; HOLD are reason provider și Resume manual conform §5.3; din orice stare activă `STOPPING → STOPPED`; finalizare normală `COMPLETED` sau `LIMITED`; crash/efect incert `NEEDS_RECONCILIATION`. READY expiră dacă preflight/model/auth/policy se schimbă. Engagementul editabil este distinct de runul imutabil.

`TaskAttempt`: `QUEUED → BOUND → RUNNING → SUCCEEDED | INCONCLUSIVE | BLOCKED | FAILED | CANCELLED | NEEDS_RECONCILIATION`. `SUCCEEDED` înseamnă procedura încheiată cu MethodCheck COMPLETE (§9.10), nu finding confirmat sau toate review-urile campaniei terminate. Retries creează attempturi noi și păstrează istoricul.

`Action`: `PROPOSED → APPROVAL_REQUIRED | DENIED | ADMITTED → DISPATCHING → COMPLETED | FAILED | UNKNOWN`. `DISPATCHING` se persistă înaintea bytes upstream; crashul în acea fereastră rămâne conservator `UNKNOWN`, chiar dacă este posibil să nu fi fost trimis nimic. Comanda operatorului poate fi idempotentă; efectul pe țintă nu este deduplicat magic.

`Finding`: candidat → validare → `CONFIRMED | REJECTED | INCONCLUSIVE`. Starea remedierii este separată: `OPEN | FIXED | REGRESSED | RETEST_INCONCLUSIVE`, cu evidence noi și raport nou, fără rescrierea verdictului istoric.

**Review operator pentru raport, separat de validare:** `report_review_policy` este ales explicit în draft și fixat în revizia runului: `OPERATOR_REQUIRED` (preselectat conservator pentru un draft nou) sau `VALIDATOR_ONLY`. Primul cere `ReportReview=PENDING | APPROVED | HELD` pentru fiecare finding CONFIRMED; al doilea produce `NOT_REQUIRED`. Nu decide LLM-ul și nu derivăm cerința din culoarea severității. Păstrăm actorul, `claim_revision`, evidence manifest/version, `review_revision` și auditul. Acceptarea manuală nu produce CONFIRMED. Acceptarea cere ownership, revizie curentă și evidence disponibile; Hold respectă ownership/revizia fără a pretinde verificarea bytes lipsă; schimbările materiale ale claimului/evidence version invalidează acceptarea. La generare sunt eligibile numai findingurile tehnic CONFIRMED cu review APPROVED sau NOT_REQUIRED. Raportul păstrează copia stării la generare; deciziile ulterioare nu rescriu snapshotul anterior. Contractul de date UI este în specificația UI/UX §8; acest flux este propus, nu implementat în backend.

**ReportReview nu blochează COMPLETED** și nu menține modelul pornit: este o coadă editorială, separată de operational Action/Approval. Accept/Hold pot urma unui run STOPPED/COMPLETED, cu aceleași controale de ownership/revizie, fără a relansa execuția. În predicatul de mai jos „approval restant” înseamnă permisiune operațională/efect, nu includerea în raport.

**Predicat de finalizare:** numai supervisorul poate închide runul. `COMPLETED` cere frontiera de discovery epuizată în subsetul declarat, toate celulele obligatorii aplicabile cu rezultat probatoriu, toți candidații validați, niciun task/inbox/review metodologic promis/approval/cleanup/efect UNKNOWN restant și runtime/executori quiescenți. Propunerea Brainului de închidere nu este autoritate. Lucru restant din limită, policy/auth/unsupported relevant sau stagnare → `LIMITED` cu lista exactă; efecte externe nereconciliate → `NEEDS_RECONCILIATION`, chiar dacă raportul parțial poate fi exportat. Stagnare implicită: trei tururi consecutive fără observație/dovadă/precondiție nouă, consum de rezultat nou sau schimbare justificată de task; retries identice nu resetează contorul. Pragul este fixat în run manifest. `COMPLETED` certifică obligațiile catalogului în misiunea și scope-ul declarat (§9.3), nu siguranța întregii aplicații. Criteriile funcționale au outcomes separate; FAIL funcțional nu este automat vulnerabilitate sau run neterminat.

### Stop, pause, sănătate

**Progresul nu este stare de control.** `RunProgress` este proiecția server-side a supervisorului, cu `phase=PREPARE|RECON|INVESTIGATE|VALIDATE|FINALIZE|UNKNOWN`, `phase_active`, `phase_updated_at` și activitate redactată bounded. Faza rezultă din lucru admis și tranziții de domeniu, nu din textul Brainului; la activități mixte validarea are prioritate în rezumat, iar taskurile individuale rămân vizibile în stream. `phase_active=false` când runul nu este RUNNING. PAUSING/PAUSED/STOPPING/STOPPED/NEEDS_RECONCILIATION au precedență în banner; ultima fază poate rămâne numai etichetată istoric. Re-renderul, review-ul unui finding sau SSE replay nu pot reactiva faza. Barele requests/timp și coverage nu sunt un procent de „pentest complet”.

Stop nu cere confirmare modală: revocă `fencing_epoch`, blochează noi dispatchuri, anulează Runnerul și închide admiterea senderului/contextelor/proceselor și așteaptă quiescența. UI rămâne `STOPPING` cât verificarea nu e completă. La timeout, supervisorul comandă terminarea process groupului prin adaptorul executorului; watchdogurile locale sunt fallbackul bounded. Numai launcherul host poate opri containerele conform §4.3. Dacă un adaptor nu răspunde, supervisorul afișează escaladarea și efectele incerte, fără `STOPPED` sau dovadă de quiescență inventată; operatorul poate folosi oprirea de urgență a instanței. Nu declarăm anularea requesturilor deja expediate. Bariera `InstanceControl` se aplică suplimentar la shutdownul aplicației, nu numai fencingul runului curent.

Pause oprește **dispatchuri noi**, nu numai taskuri noi; acțiunile deja expediate se pot drena în timeout. Permituri emise dar nefolosite sunt invalidate. SDK-ul nu produce apeluri noi în pauză/HOLD; dacă un client nu poate fi drenat sigur, îl închidem și reconstruim execuția din checkpoint persistent la Resume explicit. Resume face preflight și reconciliere, nu reînvie threaduri.

Defaults de fixture, de confirmat prin probe: maximum doi copii; o acțiune target în zbor; maximum o cerere/secundă per origin fără burst; deadline per cerere 15 secunde; lease 5 secunde, heartbeat 1 secundă; Stop fără dispatch nou după commitul revocării, quiescență locală în 10 secunde sau escaladare vizibilă. Ceas monotonic pentru deadline local, UTC pentru audit. Nu sunt performanțe măsurate.

Health: probe incluse în scope/buget, baseline la preflight; 429 respectă `Retry-After` în limite, altfel backoff bounded; 503 sau trei eșecuri consecutive de health blochează noi dispatchuri și cere review. Nu reluăm mutații pe retry automat. Bugetul global include login, redirecturi, subresurse, health, baseline/control și validare. Costul AI estimat/necunoscut este separat de hard caps de timp/request; plafon financiar numai dacă poate fi rezervat/verificat înaintea apelului sau impus la provider.

| M1 → M2 adaugă o operație independentă, fără schimbarea obiectivului sau a precondițiilor lui A | Rezultatul A/M1 este păstrat sub M1 | ResultQualification poate lega aceeași dovadă de obligația identică din M2; fără replay pretins sau copie de verdict oarbă | Brain consumă delta o dată; nu relansează A numai pentru că a crescut revizia |
| Auth/target state/business precondition invalidate pentru A | Receiptul autentic rămâne istoric; invalidarea este explicită | REVALIDATION_REQUIRED/INELIGIBLE; nu covered/FIXED/confirmare proaspătă | Task/attempt nou numai cu precondiții și authority refăcute; buget consumat rămâne contabilizat |
| Rezultat după PAUSING/PAUSED/STOPPING/STOPPED ori epoch revocat | Canal receive-only acceptă captură/usage ale execuției deja expediate și validează mappingul istoric, nu acordă citiri/tools noi | Fără promovare automată; reconciliere deterministă sau review explicit poate folosi probe deja obținute, fără noi efecte/model și fără a reactiva runul | Niciun wake/model/dispatch. Inboxul este marcat HELD_FOR_RECONCILIATION, nu ready-to-run |
| Duplicat identic înainte/după M2/Stop | Același receipt/result ID; fără event/usage dublu | Citirea disponibilității actuale nu schimbă conținutul rezultatului istoric | Niciun consum/wake dublu |
| Attempt/issuer/context străin sau payload diferit pentru rezultat deja acceptat | Refuz de asociere/conflict; diagnostic minim/quarantine bounded, fără a atașa date unui caz străin | Nicio calificare | Niciun wake sau grant |

`ResultQualification` este RecordEnvelope cu `result_ref: Ref`, `assignment_ref: Ref`, `evaluated_against_mission_ref: Ref`, `denominator_revision: Revision`, `precondition_state_refs: Ref[]`, `evidence_manifest_ref: Ref`, `decision: ELIGIBLE/INELIGIBLE/REVALIDATION_REQUIRED`, `reason_codes: Key[]`. `tasks` verifică header/producer/consum, `validation/coverage` aplică predicatele de compatibilitate/oracle și disponibilitatea curentă. Compatibilitatea este deterministă pe scope/cerere fixate, procedură/bound inputs, operație/parametru, identitate/principal/epoch și precondiții de stare; nu scor Jev sau similitudine a sumarului. În lipsa dovezii de compatibilitate, se păstrează istoricul și se cere revalidare. Eventul de invalidare trebuie să ajungă înaintea următorului dispatch; assignments neafectate pot continua, cele afectate sunt fenced/blocate. Schimbarea materială a obiectivului rămâne Stop + run nou.

**Trei chei, trei scopuri:** `RedeliveryKey=(producer_id,event_id)` elimină numai retransmiterea aceluiași eveniment. `ObligationKey` identifică structurat runul/misiunea, invariantul testat, operația/parametrul și contextul business/identității; titlul liber al ipotezei nu este identitate. `ExecutionKey` adaugă rolul, procedure/bound-input/config digests, auth_epoch și starea materială consumată. Două roluri investigator/validator nu se deduplică între ele. Bound-input digest este o proiecție versionată a valorilor/identităților materiale consumate, nu hashul întregului RecordEnvelope/BoundProcedure: exclude UUID/timestamp/revizia globală M1/M2 când nu schimbă semantica, dar păstrează identificatorii reali ai obiectelor țintă, parametrii și bytes relevanți. Aceleași sloturi/procedură/stare sub M1 și M2 aditiv au aceeași cheie de execuție; schimbarea reală a obiectului/inputului are alta. Proiecția aparține compilerului/procedurii review-uite, nu unei reformulări LLM. Input/procedură/parametru/precondiție material diferită păstrează investigația legitimă; numai reformularea textului, UUID nou sau un event duplicat nu justifică repetarea. Reopen cere basis refs noi relevante ori comandă explicită auditată; nu șterge occurrence/evidence anterioare și nu resetează limitele/stagnarea fără progres real. Cache PURE și semantic task dedup nu sunt același mecanism.

**Promisiune versus selecție:** `CoveragePromiseRevision` conține `family_keys: Key[]`, `procedure_requirements: {technique_key: Key, procedure_key: Key?, required: bool}[]`, `operation_inclusion_rule_ref: Ref`, `identity_rule_ref: Ref`, `exclusion_refs: Ref[]`, `done_rule_refs: Ref[]`. Profilul și RunSnapshot păstrează `coverage_promise_ref: Ref` separat de `selected_action_refs`/closure executabilă. Promise poate numi o metodologie cunoscută dar unavailable; nu o face executabilă. Numitorul se materializează din promisiune + inventarul cunoscut + misiune, nu numai din handlers enabled. Disable/unsupported/skipped în aceeași promisiune lasă gap; reducerea explicită a promisiunii este revizie/run nou cu diferența afișată în Review. N/A necesită dovadă de neaplicabilitate; suprafața outside-objective este neinclusă, nu sigură.

**Bootstrap focused cumulativ:** FULL_ASSESSMENT folosește selection_rule_ref către regula trusted a profilului/promisiunii pentru discovery în scope, cu bugetul runului; RESOLVED înseamnă misiune delimitată, nu inventar epuizat, iar listele de operații cunoscute cresc fără a pretinde observare/testare. În full, bootstrap_budget_ref este null și câmpurile discovery_bootstrap au liste goale/limite zero (nefolosite); nu aplicăm accidental plafonul focused întregii campanii. FOCUSED_TEST păstrează întotdeauna `bootstrap_budget_ref: Ref` către definiția imuabilă de buget cu cheia `(run_id, mission_id, FOCUS_BOOTSTRAP)`. Consumul/rezervările sunt în ledgerul curent al acelei definiții, nu în hashul unui counter mutabil; fiecare admitere citește ledgerul sub lock. Plafonul inițial și deadline-ul absolut nu se refac. Prima admitere setează deadline-ul; toate reviziile aditive/re-entry/restart citesc aceeași rezervă și consumul ei, nu recreează max_actions sau ceasul. Fiecare request, redirect și subrequest de discovery consumă din ea și din bugetul runului. Login/health de suport sunt contabilizate separat și explicit, fără a fi folosite ca discovery mascat. Pause nu reînnoiește termenul. Epuizare fără rezoluție → clarificare/gap/LIMITED, nu încă o fereastră. Clarificarea poate rezolva focusul din facts existente fără trafic; dacă mai cere discovery peste plafon, se oprește și cere run/revizie nouă, nu refill prin STEER.

**Clarificare:** P-FOCUS consumă seam-ul STEER/B18a, de aceea depinde de P-LOOP. Comanda păstrează mission/plan revision și command ID, trece prin inbox/readback ADMITTED/CONSUMED și nu schimbă material cererea. UNRESOLVED → clarificare validă → BOUNDED/RESOLVED este probă pozitivă; stale/material change/duplication sunt negative. Nu se adaugă un run status ad-hoc: Needs you este blocaj/activitate în proiecția existentă, iar Stop rămâne disponibil.

**Progres normativ:** RunProgress adaugă `phase_key: Key?`, `subphase_key: Key?`, `instance_id: Id?`, `plan_revision_ref: Ref?`, `primary_task_ref: Ref?`, `active_task_refs: Ref[]` (bounded), din PlanInstance/Task/Event la același cursor. Null este permis înainte de plan/subfază; UI nu completează din chat. La lucru mixt, prioritatea rezumatului este VALIDATE → INVESTIGATE → RECON → PREPARE; FINALIZE numai după drenarea muncii anterioare, iar lista activă păstrează celelalte taskuri. `phase_active` cere lucru admis în curs și RUNNING; așteptarea unei clarificări fără lucru în zbor nu este activitate falsă. Starea PAUSING/STOPPING etc. are precedență și nu poate fi inversată de un rezultat tardiv/rerender.

**Completion și Stop:** o ramură research opțională anulată/drain-uită nu ține raportul deschis dacă nu lasă obligație obligatorie nesatisfăcută. O obligație promisă fără rezultat rămâne gap/LIMITED. Stop revocă și cleanup nou: nu se expediază DELETE/login/logout sub permit vechi „pentru curățare”. Obligațiile cleanup cunoscute se consemnează; efectele UNKNOWN impun reconciliere. Cleanup ulterior cere comandă/run nou explicit autorizat, în aceleași scope/riscuri, nu autoresume. Refreshul legitim de auth poate scoate celulele vechi din coverage și poate duce la LIMITED pe sesiuni scurte; MVP nu transferă automat coverage între epochs. Eventuala requalificare cere dovadă explicită de echivalență și un gate separat, nu heuristica „același user”.

Probe B06/B10f/B18a/B18b/B19: M1 valid după M2 aditiv versus M1 cu auth invalid; duplicates înainte/după Stop; două proceduri cu step control omonim; două re-entry care nu refac bootstrap budget; disable fără micșorarea promisiunii; refresh/re-entry/Stop cu aceeași instanță în plan/summary/UI. Acestea sunt contracte de implementat, nu rezultate runtime ale review-ului.

## 7. Policy și efecte

Scope entry: origin exact, port, reguli de path, `ATTACKABLE | VISIT_ONLY | BLOCKED`, excluderi, dependințe, identități și interval. BLOCKED câștigă; VISIT_ONLY permite numai operații funcționale declarate și nu payloaduri de test. URL-urile din JS/OpenAPI și redirecturile nu lărgesc scope-ul.

Effect class: `READ_ONLY_KNOWN`, `SESSION_CHANGE`, `LIMITED_WRITE`, `DESTRUCTIVE`, `UNKNOWN`. Proveniență: fixture manifest/operator cu revizie; clasificarea modelului este sugestie, nu permisiune. `UNKNOWN` este blocat sub politica read-only. Pentru aplicații proprii mai puțin descrise operatorul poate aproba o operație/workflow limitat după inspecție; nu pretindem recon read-only universal al oricărei aplicații.

Approval = acțiune exactă + hash semantic verificat al argumentelor + origin/operație/identitate/epoch/policy revision + expirare + număr de utilizări. Corpul cu CSRF volatil se leagă de o rețetă versionată și de câmpuri substituibile strict definite; nu hashăm bytes vechi și apoi autorizăm orice body nou. Toate subrequesturile browserului primesc verificare proprie; „am aprobat un click” nu este autorizație nelimitată pentru requests necunoscute.

Verificarea autorității/fencingului, rezervarea bugetului și consumarea unică a approvalului sunt tranzacționale. Aceeași idempotency key cu payload diferit produce conflict. Limita de doi copii include validatorul; validarea nu poate crea pe ascuns al treilea copil. Retryurile de target ale clientului HTTP și proxyului sunt dezactivate; un retry necesar loginului sau unei probe este acțiune nouă cu buget și politică, nu retry de transport invizibil.

Scope parsing este distinct de normalizarea hărții. Pentru primul traversal-canary, ruta HTTP rămâne o operație clar autorizată, iar inputul de traversal este un parametru declarat; nu relaxăm blocarea căilor de rutare ambigue/encodate pentru a obține un finding. Inputul autorizat este păstrat exact, nu „reparat” de normalizator.

Setup/login/workflowuri simple au pași tipizați, precondiții și verificare finală; nu avem DSL general sau shell arbitrar. Operațiile cu modificare țin un jurnal de obiecte create și obligații de cleanup. Cleanupul este tot acțiune autorizată, nu o excepție de ștergere. `cleanup_incomplete` intră în raport.

## 8. Identități, auth și adevărul regulii business

Identitate = label operator, principal/rol/tenant verificabil, auth mode, referință secretă și `auth_epoch`. Anonymous este valid și nu necesită seif. Basic/token/cookie sunt injectate numai în originea permisă, cu redirecționări revalidate; login asistat rulează în browserul engagementului, fără import automat de profil personal.

**Seif target:** criptare AEAD cu bibliotecă consacrată, cheie locală separată de DB și backup, permisiuni 0600, referințe opace în DB; cheia lipsă produce LOCKED. Nu pretindem protecție de același UID. Copiile temporare de cookies/storageState au TTL, sunt private, excluse din Git/export și șterse la închidere conform retenției. Operatorul introduce secrete doar în UI securizat, niciodată în chat/model.

Lease exclusiv per auth context și, unde este necesar, obiect de test. Un singur refresh owner; după refresh, epoch nou și precondiții revalidate. Nu clonăm orbește refresh tokens între doi workeri. A doua identitate poate avea alt context independent, dar limita globală rămâne. UI arată `WAITING_FOR_IDENTITY` în locul unui worker aparent blocat fără explicație.

Refreshul este efect de sesiune: persistăm intenția `(refresh_attempt, old_epoch, owner_generation, fencing)` înaintea cererii. Noul secret se salvează criptat/durabil înaintea publicării noului auth_epoch în tranzacție; numai ownerul încă valid poate publica. Un răspuns de la owner expirat este pus în carantină și contextul se blochează pentru reconciliere, nu redevine valid printr-un CAS asupra epochului vechi. Crash după rotația serverului dar înaintea persistării locale → `AUTH_UNKNOWN`, fără retry cu tokenul vechi; reautentificare asistată ori reconciliere explicit suportată de aplicație. G03b injectează ambele ferestre și refuză rezultate negative/verdict în intervalul incert.

Matrice business versionată: `(principal/rol/tenant, obiect sau clasă de obiect, operație) → ALLOW | DENY | UNKNOWN`, sursă și revizie. Include obiect privat și partajat. `owner != actor` sau status 200 nu sunt oracle. UNKNOWN produce `INCONCLUSIVE` și cerere de context; nu poate fi completat de LLM ca fapt.

Pozitiv login: o observație configurată de principal/rol (nu doar absența 401). Drift/expirare între baseline și probă invalidează intervalul. Browser storage și HTTP cookie jar sunt contexte distincte până când un transfer explicit testat dovedește echivalența. Replay recuperează tokenuri volatile și reface setupul; auth expirat nu devine `tested_no_issue` sau `FIXED`.

### 8.1. Stocare criptată comună și transfer write-only

Un singur mecanism de credential store pentru API keys T1 și secrete target la B09h; namespace/provider și target identity rămân distincte. **Bootstrap explicit** la prima configurare: ownerul supervisor creează o cheie master aleatoare și un fișier AEAD cu bibliotecă consacrată admisă în T1. Stocare privată de instanță în afara Git/release, directoare 0700 și fișiere 0600, owner/mode și no-symlink verificate. Cheia master este separată de DB și backupul obișnuit, accesibilă numai ownerului în topologia de produs; deblocare automată la pornire dacă cheia și ciphertextul sunt valide. Nu cerem parolă la fiecare restart și nu adăugăm serviciu de seif/keyring/TPM. Cheia este **niciodată regenerată automat** peste un seif existent: absentă/invalidă/permisiuni nesigure → LOCKED; reinstalarea nu distruge secretele. Nu promitem protecție de root/same-UID sau de copia care include și cheia master.

Traseu **write-only**: formular local paired → API cu Host/Origin/CSRF și body limitat → comanda privată de supervisor → seif. Secretul tranzitează memoria UI/API, nu localStorage/sessionStorage, URL, argv, environment global, audit payload, prompt, trace, log, răspuns de validare sau export. API de reveal absent; readback doar presence/ref/revision/status. Ownerul injectează secretul numai senderului/identității autorizate; ștergerea referințelor din memorie nu este garanție de zeroizare Python. Save nu validează cheia online.

Ref opac leagă secret_id/revision/namespace/instance; DB conține numai metadata, revocare și referințe. AEAD autentifică și aceste asocieri; înlocuirea fișierului sau referinței nu poate schimba contul tacit. Un singur writer serializat în ordinea §5: pregătește revizia criptată (păstrând reviziile încă referite), scriere temporară privată → fsync fișier → rename atomic → fsync director → tranzacție DB publică noua referință și receiptul idempotent. ACK numai după commit confirmat. Crash înainte de publicare lasă revizie orfană neutilizabilă, reconciliabilă; DB ref fără ciphertext valid blochează folosirea. Nu ștergem vechea revizie înaintea activării durabile și nu pretindem atomicitate DB–filesystem. Intenția/receiptul nu păstrează secretul sau un hash simplu al valorii lui; deduplicarea secret-bearing este privată/keyed și legată de command ID.

Înlocuire/rotație: revizie nouă salvată, apoi activare/revocare atomică în DB; utilizările noi ale reviziei vechi sunt refuzate și execuțiile afectate drenate, fără hot-swap. **revocare** locală posibilă și când seiful este LOCKED; aceasta nu revocă cheia upstream. Cheie compromisă cere revocare și la provider. Metadata/istoricul nu sunt șterse; retenția ciphertexturilor referite este explicită.

**backup/restaurare minimă:** cu writerii opriți, DB + fișier criptat + manifest de revizii coerente; cheia master este salvată separat prin procedură privată explicită, niciodată în exportul normal. Restore în root nou pornește fără execuții/granturi reutilizate, verifică perechile DB/secret și cere reactivarea explicită a conexiunilor; o copie veche nu reactivează tacit o cheie revocată. Fără master key istoricul nesensibil rămâne citibil, secretele nerecuperabile. Teste T1: restart/autounlock, cheie lipsă/greșită, secret echo, crash file↔DB și revoke între admitere/send; readerii nu pornesc providerul.

### API Omnis v1 (contract propus, nu endpointuri deja existente)

- `/api/v1/engagements`, `/{id}`, `/{id}/revisions`: CRUD draft și validare; update cu `If-Match`/revision, 409 la conflict sau run activ.
- B09h introduce `GET/POST /api/v1/engagements/{id}/identities`, `GET/PUT /api/v1/identities/{id}` și `POST /api/v1/identities/{id}/verify`, deținute de identities/vault. Editarea identității în draft cere CAS/sesiune/CSRF și run oprit; secretul se persistă numai în seif, citirile expun handle/status/configured, niciodată valoarea. Verify login este acțiune funcțională autorizată, bugetată și atribuită, nu atac auth: 202 este receipt, iar readback verifică principal/rol/auth_epoch și evidence; invalid/expired/cross-engagement sunt refuzate. Reautentificarea unui run urmează ownerul/lease-ul și noul epoch din §8, nu un PUT care schimbă tacit identitatea. Formularul HTTP este disponibil cu B09h/G-AUTH-HTTP, assisted browser cu B09b/G03b; niciun endpoint nu este implementat prin acest document.
- Orice Start/Resume și admitere de lucru verifică și `InstanceControl` în tranzacția comună; `INSTANCE_SHUTTING_DOWN` refuză lucrul nou chiar dacă runul anterior este deja STOPPED. Citirile și Stop rămân disponibile.
- `/{id}/preflight`, `/{id}/runs`, `/runs/{run}/commands`: Start/Pause/Resume/Stop; comenzi cu idempotency key și readback; 202 înseamnă acceptată, nu finalizată. Serverul reface condițiile critice la Start, nu se bazează pe un rezultat UI stale.
- `/runs/{run}/events?after=cursor`: SSE cu `id`, replay din DB, heartbeat, last cursor; cursor expirat → `RESYNC_REQUIRED`, fetch snapshot și reabonare fără dublare. Snapshot include `through_cursor` consistent.
- `/runs/{run}/surfaces`, `/coverage`, `/tasks`, `/findings`, `/approvals`, `/evidence/{id}`: query bounded și scope validat. Autorizarea nu vine din filtrul clientului.
- `/settings/providers/{allowed_provider}/...`, `/settings/runtime`, `/settings/skills/...`: operații allowlisted, nu pass-through către Hermes.
- `/reports` și `/findings/{id}/retests`: snapshoturi imutabile și revalidare țintită cu buget/autorizație proaspete.

Errors: `{code, message, correlation_id, field_errors, retryable}`; fără traceback/secrete. Exemple: `SCOPE_DENIED`, `UNSUPPORTED_TRANSPORT`, `AUTH_BLOCKED`, `POLICY_CHANGED`, `EVIDENCE_UNAVAILABLE`, `RUNTIME_INCOMPATIBLE`, `NEEDS_RECONCILIATION`. Semantica retryable se referă la operația API, nu la reexpedierea automată pe țintă.

OpenAPI generat din Pydantic; tipuri TS generate în build. Tipurile generate nu sunt validator runtime și nu acordă drepturi; API validează tot. TanStack Query deține server state, URL deține filtre/selecția, React deține state local al formularului; fără Redux/Zustand inițial. Invalidări SSE pe entity revision și refetch, nu counter++ la orice event repetat.

### 9.1. Proiecții pentru cockpit, cursor și consistență

Contractul de citire este `ProjectionEnvelope`: `schema_version`, engagement/run explicite (sau context global), `scope_revision_id`, `through_cursor`, `as_of`, `data_state`, `data`, iar pentru colecții `next_page`/`has_more`/limita. `data_state` și disponibilitatea metricilor disting NOT_RUN/UNAVAILABLE/UNKNOWN de un zero măsurat. `scope_revision_id` este configurația imutabilă; `through_cursor` este versiunea datelor citite. Același scope poate avea coverage diferit după ștergerea evidence, la alt cursor; nu numim ambele același snapshot de date. În envelope-ul global `through_cursor=null`; cardurile poartă contextul/cursorul propriului run, iar `as_of` global nu poate fi folosit pentru SSE resume. Cursorul de pagină este legat și de filtre/sortarea keyset, nu poate fi mutat între queries.

Proiecția unei pagini — inclusiv counts de navigare și rezumat — se citește într-o tranzacție PostgreSQL read-only REPEATABLE READ, închisă înainte de orice I/O lent. Summary, Top findings, atenția și legenda unei pagini nu sunt cereri independente amestecate în frontend. Citiri separate poartă versiunea lor: clientul păstrează ultima proiecție completă ca stale până la înlocuirea coerentă, nu combină contoare de la cursori diferiți. Nu ținem tranzacții DB deschise între clickuri/pagini și nu construim un motor generic de time-travel în P0.

| Contract propus | Owner / semantica obligatorie |
|---|---|
| `GET /api/v1/dashboard` | `engagements` + proiecții `runs`: active run separat de engagementul selectat, atenție tipizată, sumar global și pagină de engagementuri. Globalul nu este suma paginii clientului. Pentru fiecare engagement alegem runul activ sau cel mai recent; nu însumăm runuri/retesturi istorice. Fără run → NOT_RUN, fără date demo. |

Secvența durabilă rămâne **per engagement** în ordinea commiturilor (§6). Cursorul opac de transport leagă schema/contextul engagement/run și secvența; streamul unui run filtrează jurnalul engagementului și poate avea goluri legitime. Snapshotul include `through_cursor` din aceeași citire; abonarea pornește strict după acesta, iar duplicate/out-of-order nu scad revizia sau dublează UI. ID-ul unui eveniment și cursorul nu sunt autorizație. SSE session expiry închide fluxul și cere reautentificare, nu dezactivează verificarea ownership.

Home revalidează sumarul la focus/mutări și prin polling bounded numai cât pagina este vizibilă; când există run activ, evenimentele lui pot invalida aceeași query. Nu inventăm un cursor global din mai mulți cursori per engagement. `as_of`/staleness sunt vizibile; Stop rămâne legat de ID/revizie chiar dacă între citiri s-a schimbat runul activ. Câmpuri agregate disponibile numai parțial sunt marcate astfel, nu completate cu zero.

Aceste DTO-uri se introduc incremental: B01b fixează envelope/error/revision; B03/B04 primul Dashboard real; B08 evenimente/stadiu/bugete; B10/B12 coverage; B13 findings/review/report. Existența contractului nu cere toate tabelele și endpointurile în P0.

### 9.2. Report review și snapshotul exportabil

`POST /api/v1/findings/{id}/report-review` este comanda propusă, deținută de `findings/report_review.py`: decision APPROVED/HELD, run/context, expected `claim_revision`, evidence manifest/version și `review_revision`, cu If-Match și command ID. Body-ul nu furnizează verdict, bytes sau o listă arbitrară de findinguri confirmate. `GET /api/v1/runs/{run}/findings` oferă starea curentă și auditul bounded; receiptul unei comenzi nu înlocuiește readbackul.

- Ownership, sesiune/CSRF, policy fixată, CONFIRMED și reviziile sunt verificate server-side. Accept cere evidence necesare disponibile, integre și legate de claim. **Hold este permis și când evidence sunt indisponibile**, fiind excludere, nu validare. Policy VALIDATOR_ONLY nu expune aceste mutări; required/status vin de la backend.
- `claim_revision`/manifestul descriu materialul verificat; `review_revision` descrie decizia operatorului. Accept/Hold nu incrementează claim_revision și nu își invalidează singure materialul. Material nou creează review PENDING când policy cere operator, altfel NOT_REQUIRED, și păstrează decizia veche istoric; CONFIRMED trebuie să aparțină claimului/manifestului citat, nu se moștenește de la o versiune veche necorespunzătoare; schimbarea disponibilității singură nu o rescrie.
- Use case-ul folosește UoW/CAS, FK de ownership și unicitate per legătură run/finding/claim/manifest/policy. Comanda identică repetată returnează același receipt, fără revizie/audit/event dublu; aceeași cheie cu alt payload → conflict. O comandă stale nu aplică decizia pe materialul nou. După verificarea bounded a bytes, commitul verifică reviziile/proveniența; retenția/invalidation concurentă nu poate lăsa o acceptare nouă pe un manifest schimbat.
- `POST /api/v1/runs/{run}/reports` creează din DB un snapshot coerent al setului eligibil la momentul generării, nu din lista trimisă de browser. `GET /api/v1/runs/{run}/reports` listează istoricul; `GET /api/v1/reports/{id}/artifacts/{format}` livrează HTML/JSON numai după ownership/integritate/AVAILABLE. Idempotency leagă aceeași cerere de același snapshot; raportul nu se regenerează din findings curente la download. Materializarea bounded este job durabil al supervisorului, nu BackgroundTask volatil în workerul API; admiterea lui verifică InstanceControl și nu pornește model/target. Shutdownul instanței îl drenează/reconciliază, separat de Stop assessment.
- Snapshotul îngheață IDs/revizii/material redactat, review/policy, scope, mission/focus/coverage_promise refs, through_cursor/denominator, starea runului, excluderi/motive, disponibilitatea evidence și versiunea rendererului. JSON/HTML au DTO allowlist; fără material_snapshot intern sau alte copii ascunse ale bytes indisponibili. Exportul folosește protocolul STAGING→AVAILABLE din §10, caps și reconciliere; queued/202 nu este download ready. Failure și reîncercarea idempotentă nu mută snapshotul spre date mai noi.
- Raport parțial este permis când runul este neterminat/LIMITED sau există excluderi/limite, dar spune explicit ce lipsește. Nu numim un raport gol „aplicație sigură”. Un finding legat prin occurrence confirmată sau retest autorizat în RunFindingLink este numărat o singură dată; retestul citează claimul istoric și probele noi, fără duplicarea vulnerabilității. Disponibilitatea curentă nu șterge verdictul, dar exportul nou nu reproduce bytes declarați indisponibili. ReportReview nu este un grant de efecte, chiar dacă este realizat în timpul unui run.

### 9.3. Misiune: general sau focalizat

**HF01–HF03, adoptate:** concretizăm obiectivul existent; nu creăm chat DB sau două câmpuri de obiectiv. Contractele de mai jos sunt normative pentru B02/B04/B06/B10–B13, nu endpointuri implementate în P0.4.

Tipuri comune pentru §9.3–9.6: `Id` = UUID opac; `Revision` = integer ≥1; `Digest` = SHA-256 lowercase hex, 64 caractere; `Ref` = obiect strict `{kind: enum din registrul trusted, id: Id, revision: Revision, digest: Digest}`; `Cursor` = token opac verificat pe context; `Text` = string Unicode, fără coerciții. Toate câmpurile din tabele sunt obligatorii; numai `T?` acceptă null, iar `T[]` acceptă lista goală dacă nu se precizează minim. Niciun câmp suplimentar nu este ignorat; schema necunoscută se refuză. Metadata declarativă nu acordă autoritate. Ref-urile se rezolvă cu ownership, tip/revizie/digest și compatibilitate, nu doar prin existența ID-ului. Referințele la catalog sunt globale numai pentru releases publicate; excepția CandidateSnapshot pentru PACKAGE_EVAL este privată și limitată conform §9.8. Cele de caz sunt strict engagement/run-scoped. Tipurile se materializează în DTO/schema generată cu primul consumator, nu ca stuburi acum.

**Adresabilitate și digesturi fără ciclu:** `CanonicalJSON` înseamnă UTF-8 JSON cu chei sortate lexicografic, separatori compact `,`/`:`, ensure_ascii=false, fără BOM/newline, duplicate keys/NaN/Infinity interzise; numerele non-integer sunt decimal strings canonice (`0` sau fără zerouri inițiale/finale redundante). Array order este semnificativ; textul nu se normalizează. Regula de bytes este aceeași folosită pentru lista de fișiere §9.4. Pentru înregistrări persistate, backendul creează `RecordEnvelope={schema_version:1, kind:Key, id:Id, revision:Revision, payload:object strict, digest:Digest}`; `digest=SHA256(CanonicalJSON({schema_version,kind,id,revision,payload}))`. Digestul propriu este omis, nu înlocuit cu placeholder. Fiecare revizie este imuabilă; răspunsul modelului nu își atribuie record ID/revision. Tipurile care afișează id/revision/digest în tabele sunt forma aplatizată a acestui envelope (câmpurile nu se dublează în payload). PromptBundleRevision folosește exact această regulă pe payloadul cu toate base/role/package refs, composer/tokenizer și limite; nu hash-uiește propria valoare digest. TaskBriefV1 și TaskResultV1 primesc separat envelope-uri backend cu kind `task-brief` și `task-result`, ID-uri și revizii proprii. `brief_revision` din header este revizia brief-ului, **nu** cea a rezultatului; CriterionOutcome.task_result_ref se rezolvă la envelope-ul exact al rezultatului acceptat. Rezultat duplicat identic are același receipt; alt payload pentru aceeași cheie attempt/result cere conflict/reconciliere, nu overwrite.

Excepția explicită de conținut pentru Ref la catalog: package/technique/procedure/schema/overlay/file din același release poartă **digestul pachetului**, calculat din bytes sursă §9.4, nu hash-uri recursive ale indexului rezolvat. Backendul leagă `(kind,id,revision)` de package release și key/path unic; verifică și conținutul fișierului manifestat. Astfel Technique→Procedure→Technique nu creează hash autoreferențial. Referințele la alte releases sunt Ref externe deja fixate; dependency cycles între releases sunt refuzate. Alte Ref (mission, focus, snapshots, rezultate, evidence metadata) folosesc RecordEnvelope; pentru bytes artifact, digestul bytes este câmp separat în payload, verificat la citire. Aceste reguli nu cer un tabel nou per concept, ci adresabilitate/revizii la primul consumator.

### 9.4. Catalog: pachet, tehnică și procedură

**HF04.** `settings/skill_catalog` deține catalogul; loaderul de produs citește numai releaseurile/metodologiile fixate și admise, fără descoperire automată a oricărui SKILL.md. `skills/` este sursa de produs; `.hermes/skills/` este numai dezvoltare. Layoutul de pachet păstrează forma:

```text
skills/object-authorization/
  SKILL.md
  omnis.yaml
  references/methodology.md
  references/false-positives.md
  references/technologies/<overlay>.md
  templates/procedures/read-object.yaml
  templates/schemas/task-result.schema.json
  templates/requests/<reviewed-template>.json
  assets/wordlists/<reviewed-seed>.txt
```

`SKILL.md` are frontmatter de pachet `name`, `description`, `version`, provenance; descriere scurtă și ID nativ corelat cu manifestul. Secțiuni stabile: când se folosește/nu se folosește; inputs/precondiții; ipoteză/invariant; metodă; baseline/probe/control; evidence/oracle; false positives/proof gaps; effects/limite/Stop/cleanup; output/handoff; surse/compatibilitate/evaluare. Overlay-urile sunt selectate numai pentru tehnologia/faptele relevante, nu încărcate integral. Testele upstream/adaptate, truth/canary și held-out sunt în workspace evaluator/dezvoltare **nemontat** investigatorului; nu în pachet. Helpers opționale nu rulează la import/editare; executabilul poate fi folosit numai prin adaptor trusted, niciodată shell din editor.

Tipuri suplimentare: `Key` = string `[a-z][a-z0-9_.-]{0,127}`, unic în namespace-ul registrului; `Version` = SemVer exact fără range/latest; `Path` = POSIX relativ UTF-8 ≤240 bytes, fără absolut, `..`, segment gol, backslash sau symlink; `SchemaRef` = Ref către JSON Schema 2020-12 local, fără remote/file refs; `Technology` = `{product: Key, version_scheme: SEMVER/PEP440/OPAQUE, versions: Text[], transports: Key[]}` (OPAQUE cere egalitate exactă, intervale numai prin parser trusted); `Precondition` = `{predicate_id: Key, input_refs: Ref[], expected: bool, on_missing: BLOCKED/INCONCLUSIVE}`; `Limits` = `{max_attempts: integer 1..10, max_actions: integer 1..300, deadline_seconds: integer 1..1200, max_output_bytes: integer 1..1048576, max_fanout: integer 1..2}`. Sunt plafoane cerute; runul poate numai să le restrângă. Listele nedeclarate altfel au maximum 128 elemente, Text nedeclarat altfel ≤4096 code points, fiecare DTO serializat ≤1 MiB; datele mari sunt artifacts, nu prompt inline.

Controls și step receipts din TaskResult se identifică prin `(bound_procedure_ref, step_id)`, astfel încât două proceduri cu pasul `control` să nu se amestece. Pentru `verification_kind=SECURITY`, baseline/probe/control cer fiecare minimum un pas și non_applicable_groups este gol. Pentru `CONTRACT`, probe conține minimum un pas de lucru; baseline/control pot fi goale numai cu câte un motiv explicit în non_applicable_groups (fără duplicate sau grup nevid declarat neaplicabil). Aceste grupuri denumesc verificări ale transformării/funcției, nu atacuri inventate. Oracol/checker trusted obligatoriu pentru orice procedură executabilă și outcomes includ BLOCKED/INCONCLUSIVE; oracle_ref null rămâne methodology-only. SECURITY cere oracle de familie și probe vulnerable/fixed/benign; CONTRACT cere checker de schema/transformare/funcție cu fixture validă/invalidă/incompletă/ostilă după caz. CONTRACT este independent de execution_class PURE/MODEL/IO; un pas de model sau rețea nu devine PURE prin etichetă. Checkerul CONTRACT nu confirmă vulnerabilități și nu crește security coverage; leads se întorc ca observations/next_clues. Cleanup gol cere motiv; limitele/cleanup și inputurile de identitate/business trebuie rezolvate înainte de execuție, nu completate ca adevăr de LLM. Un package template folosește sloturi tipizate pentru refs de caz; instanțierea în TaskBrief le rezolvă, fără a fixa un engagement în release global.

**Unicul manifest `omnis.yaml`:** obiect strict cu `schema_version`, `package_key`, `version`, `native_name`, `execution_preference` (ExecutionPreference? §9.9), `skill_path` (exact `SKILL.md`), `techniques` (TechniqueRevision template[]), `procedures` (Path[] în templates/procedures), `support_files`, `file_bindings: {entity_kind: Key, key: Key, path: Path}[]`, `input_schema_ref`, `output_schema_ref`, `compatibility`, `provenance`; tipurile sunt cele de mai sus. IDs/revision/template refs locale sunt declarate în manifest/fișierele sale; backendul rezervă identitățile/reviziile și rezolvă refs la înghețarea candidatului (§9.8); publicarea promovează exact acel rezultat. `publication`, `release_digest`, review/eval receipts și readiness sunt **metadata backend**, nu câmpuri autoautorizante YAML. Parent `package_ref` este rezolvat de backend după hash, nu un digest propriu scris în bytes care se hash-uiesc. Schema de template distinge referința locală de slotul de caz; regulile exacte de rezoluție sunt cele de mai jos.

**Template refs și slots — forme exacte, fără convenții ascunse:** în fișierele sursă, `TemplateRef` este union discriminat: `{kind: LOCAL, entity_kind: Key, key: Key}` pentru obiecte/fișiere din pachet sau `{kind: RELEASE, ref: Ref}` pentru release extern. Inputurile de caz folosesc `InputRef = Ref sau CaseSlotRef`, unde `CaseSlotRef={kind: CASE_SLOT_REF, name: Key}`. `CaseSlot={name: Key, expected_kind: Key, min_items: integer 0..128, max_items: integer 1..128}` se declară în `slots: CaseSlot[]` (maximum 128) al procedurii; min≤max și nume unic. Un InputRef scalar admite numai slot max_items=1; min=0 numai unde câmpul este nullable. Câmp listă admite slot bounded many; ordinea valorilor este păstrată. În template-urile sursă, partea Ref din InputRef folosește TemplateRef, nu ID-uri backend inventate.

`ProcedureTemplate` are câmpurile ProcedureRevision fără backend `id/revision`; Ref/SchemaRef de catalog sunt TemplateRef, iar inputurile de caz sunt CaseSlotRef sau TemplateRef. `TechniqueTemplate` are câmpurile TechniqueRevision fără backend `id/revision`, cu aceleași local/release refs și fără case slots. Manifestul folosește aceleași forme pentru refs. CaseSlotRef este permis **numai** în Precondition.input_refs, business_rule_refs și Step.input_bindings.source_ref; nu în technique/tool/oracle/schema refs, key, limits sau parametri liberi. Aceste trei poziții se citesc `InputRef` în tipurile din tabel pentru ProcedureRevision publicată; forma BoundProcedure cere toate Ref/CaseSlotRef statice rezolvate; StepOutputRef de mai jos rămâne legătură tipizată la outputul viitor al unui pas anterior, nu un case slot nerezolvat. Nicio valoare nu este interpolată ca text/cod. Valorile tipizate ale parametrilor sunt obținute numai prin input_bindings/schema adaptorului.

`file_bindings` declară explicit maparea `(entity_kind,key) → path` pentru orice fișier referit prin LOCAL; kind aparține enum-ului lowercase `schema/overlay/method/asset/prompt/template`. Exemplu inert: `{entity_kind: schema, key: task-result, path: templates/schemas/task-result.schema.json}`. Pathul trebuie să aparțină setului declarat prin skill_path/manifest implicit/procedures/support_files și digestului; aceeași pereche nu poate avea două paths, două bindings pentru același kind/path sunt refuzate. Technique/procedure LOCAL rezolvă `key` din definițiile parsate, package LOCAL rezolvă package_key; nu confundăm Key cu un path și nu ghicim stem-uri. Unknown kind/key sau un schema ref către overlay se refuză. Câmpul este parte din bytes omnis.yaml și din digest, nu un registru concurent.

La înghețarea CandidateSnapshot, resolverul alocă/păstrează IDs pe `(package_key, entity_kind, key)`, atribuie revision și rezolvă LOCAL/RELEASE; CASE_SLOT_REF rămâne explicit în **ProcedureRevision template publicat**, nu pretinde input de caz deja rezolvat. La assignment, `ProcedureBinding={procedure_ref:Ref, slot_values:{slot_name:Key, refs:Ref[]}[], bound_procedure_ref:Ref}` în TaskBrief rezolvă exact fiecare slot; scope/ownership/kind/revision/digest și cardinalitatea sunt verificate. Orice slot necunoscut/duplicat/lipsă/străin sau substituție în câmp fără slot este refuzată. Backendul materializează un `BoundProcedure` adresabil prin RecordEnvelope, cu `procedure_ref`, `slot_values`, `resolved_procedure` (fără case slots, cu StepOutputRef validat unde este necesar) și `mission_ref`; nu include propriul bound_procedure_ref în preimagine. Backendul creează întâi acest record, apoi îl leagă în ProcedureBinding din brief. Nu se rescrie releaseul global. Astfel „nerezolvat refuzat” înseamnă local/release refs la Publish și **orice case slot** la dispatch, nu interdicția template-urilor publicate.


Validare: YAML safe, fără duplicate keys/tags/aliases, depth ≤32, manifest ≤256 KiB; IDs unice, fișiere/referințe/schema/tehnică-părinte rezolvabile, paths confined fără symlink, no shadowing, fără handler/tool/oracle necunoscut în procedură executabilă. Known-but-uninstalled = dependency-unavailable; methodology-only poate fi publicat cu `oracle_ref=null`, dar **nu** selectat executabil. Toate fișierele pachetului trebuie declarate și incluse în digest; fișierele nedeclarate sunt refuzate. Digest release = SHA-256 al UTF-8 JSON compact al listei de `{path,sha256,size}` pentru fișierele regular complete, ordonată după bytes UTF-8 ai pathului, cheile ordonate lexicografic, separators `,`/`:`, ensure_ascii=false, fără newline/BOM. `sha256` se calculează pe bytes originali, `size` integer bytes; digestul derivat se stochează numai în backend, fără hash autoreferențial. Manifestul/procedurile originale și proveniența sunt păstrate; indexul rezolvat al backendului este derivat și leagă digestul releaseului.

**Draft → Review → Eval → Publish:** review și eval receipts aparțin backendului, leagă digestul material, author/reviewer IDs, corpus/protocol/model/tool versions și verdictul; editarea invalidează acceptările materiale. Autorul AI nu autoaprobă; traseul explicit al operatorului unic și al evaluatorului este în §9.8. Un `validated: true` inventat este respins. Publicarea methodology-only cere review/static eval; activarea executabilă cere evaluarea specifică verification_kind: SECURITY cu fixtures vulnerable/fixed/benign, CONTRACT cu controale valide/invalide/incomplete/ostile și regresii ale transformării ori funcției, conform §9.8. Un PURE_PASS nu califică executarea SECURITY. Knowledge-reviewed, dependency-ready, fixture-evaluated, benchmark-evaluated și permitted-for-run sunt axe calculate distincte. Publish/retire sunt CAS/idempotente cu audit/readback. RunSnapshot fixează releases și compatibilitatea: taskurile noi din run nu văd draftul/releaseul nou. Revocarea activă face Stop/fencing; rollback selectează un release vechi pentru runuri noi. Incompatibilitate de câmp/semantică cere schema major explicită și gate de migrare; nu interpretare parțială. Metoda/configurația evoluează fără schimbarea core-ului; protocol/oracle nou poate cere adaptor și teste.

Scope și ownership la citiri se verifică după tipul emitentului: root vede numai runul său și proiecțiile permise, copilul numai assignmentul; niciunul nu poate citi alte engagementuri sau granturi.

**Preflight inert versus probe online:** Save/Next/Back și `POST /api/v1/engagements/{id}/preflight` verifică local sintaxa, closure/revizii/readiness și receipturi deja disponibile; zero apeluri model/target/provider. „Verify login”/„Check target health” sunt comenzi online **separate**, explicite, înainte de Start, după B07/B09h și permisiune/buget. Se creează din draft o revizie imuabilă a inputului verificat, fără a îngheța editarea viitoare a engagementului. Rețeta CheckPlan se compilează din operații funcționale trusted, nu dintr-un prompt.

`CheckPlan` este RecordEnvelope cu `purpose: LOGIN_VERIFY/HEALTH_CHECK`, `engagement_revision_ref: Ref`, `scope_ref: Ref`, `policy_ref: Ref`, `identity_ref: Ref?`, `recipe_ref: Ref`, `allowed_operation_refs: Ref[]`, `max_actions: integer 1..30`, `deadline: UTC`, `data_policy_ref: Ref`. Recipe/operations sunt instalate și verificate; nu scanner, payload de atac, discovery sau origin sugerat de țintă. Intersectăm permisiunea operatorului cu aceste limite la **fiecare request**, inclusiv redirect/login support. Efectele de sesiune sunt declarate, nu mascate read-only. Seiful injectează secretele numai adaptorului; modelul nu este pornit. OPERATOR_CHECK este refuzat cât un run este activ; refreshul dintr-un run aparține ownerului AuthContext și contextului taskului afectat (§8), nu unui canal pre-run care ocolește Stop.

`CheckReceipt` leagă check/command/contextul fixat, Action/evidence refs, principal/rol/auth_epoch verificate sau UNKNOWN, usage, `expires_at: UTC` și status `PENDING/RUNNING/SUCCEEDED/FAILED/CANCELLED/NEEDS_RECONCILIATION`. API: `POST /api/v1/identities/{id}/verify` și `POST /api/v1/engagements/{id}/health-check` întorc 202/check ID; `GET /api/v1/checks/{check}` oferă readback, `POST /api/v1/checks/{check}/commands` admite numai CANCEL cu expected revision/idempotency. Dublu click identic nu repetă loginul; alt payload cu aceeași cheie dă 409. Timeout/efect incert nu devin auth ready și nu produc retry automat.

Cancel check incrementează cancel_epoch și închide admiterea, apoi drenează/reconciliază; shutdownul instanței închide și aceste dispatchuri. Bariera InstanceControl, scope/effects/approval, bugetul, egressul și evidence store sunt cele comune B07; nu există transport HTTP direct din endpoint. No new dispatch după revocare se probează la sink. Verificarea nu începe un assessment și nu acordă capabilități de hunting unui run viitor.

La Start, backendul cere profil/model/catalog admise și revalidează receipturile cerute de profil: aceeași revizie materială, identitate/principal/epoch, operații/scope/policy și termen neexpirat. Receipt stale → preflight blocat/cerere de Verify explicit, nu sondare online ascunsă sau succes reciclat. Start fixează RunSnapshot numai cu inputurile revalidate, trece prin PREFLIGHT/READY și apoi RUNNING cu faza PREPARE; prima inferență are ModelDispatch admis. Eșec înainte de admiterea runului produce command refuzat, fără run activ fictiv; crash după admitere folosește reconcilierea normală. Numai după MissionSpec/FocusEnvelope validate se pot admite taskuri target; full nu sare peste această frontieră.

G03a/G-AUTH-HTTP verifică draft→Verify fără Brain, save inert, readback/restart, secret echo/cross-identity/stale scope refuzate, anulare și shutdown între admitere/send. H04/H08 verifică separat root versus child versus emitent sistem. Niciun endpoint/context de aici nu se introduce în P0; ownerii sunt runs/commands, identities/vault, policy și executori, odată cu primii consumatori.

### 9.8. Evaluarea candidatului și publicarea fără ciclu

**F01 / C01:** rezoluția și evaluarea preced Publish. `settings/skill_catalog` îngheață materialul reviewed într-un **CandidateSnapshot**, adresabil în namespace-ul privat de evaluare, nu în catalogul selectabil pentru assessment. Resolverul verifică schema/path/closure/compatibilitate și alocă identități/revizii înainte de eval; Publish promovează acel index/material, fără rezolvare nouă spre dependencies mobile. IDs/revisions rezervate unui candidat respins nu sunt refolosite pentru alt material. Excepția îngustă de adresare pentru refs nepublicate există numai sub admiterea de evaluare a acelui snapshot; modelul/browserul nu o obțin trimițând un digest.

`CandidateSnapshot` este RecordEnvelope cu `draft_ref: Ref`, `source_draft_refs: Ref[]` (reviziile exacte ale tuturor pachetelor/profilelor/surselor co-înghețate, inclusiv draft_ref; minimum una), `material_digest: Digest`, `resolved_index_digest: Digest`, `candidate_refs: Ref[]`, `dependency_closure_refs: Ref[]`, `profile_ref: Ref`, `compiler_revision: Text exact SHA`, `technical_review_ref: Ref`, `created_by: Id`. Materialul complet se păstrează read-only sub catalog/candidates, separat de workspace-ul editabil; nu montăm checkoutul/draftul mutabil. Ref-urile candidate folosesc identitățile/reviziile rezervate și digestul conținutului conform §9.3–9.4; access check cere snapshotul de evaluare care le conține. Profilele/prompturile/recipes pot fi înghețate în aceeași closure; externele trebuie rezolvate exact, fără cycles. Digestul propriului CandidateSnapshot nu intră în preimaginea componentelor sale. TechnicalReviewReceipt de dinaintea înghețării citează material/index digests, nu Ref-ul snapshotului care încă nu există; EvaluationReceipt ulterior citează snapshotul, fără referință inversă în preimagine.

`RunSnapshot.execution_purpose` este fixat de backend: `ASSESSMENT` pentru runurile normale și retest, `CONTRACT_PROBE` pentru proba explicită a contractelor (fără provider în P2-inert; inferență aprobată separat în P2-live; întotdeauna fără target effects), `PACKAGE_EVAL` pentru evaluarea autorizată a candidatului. Nu este selector care acordă permisiuni în UI/JSON. Pentru ASSESSMENT rămân obligatorii releases publicate și capabilități evaluate/permitted; PACKAGE_EVAL permite **numai** candidatul exact din `EvaluationAdmission`, fără promovare globală. Același supervisor, RuntimeBinding, ledger B06m/B07, broker, Stop și evidence se reutilizează; nu runtime sau transport paralel. Runurile de probă/eval sunt etichetate în Settings și excluse din findings/coverage/counts normale ale engagementurilor. Retestul de securitate rămâne ASSESSMENT nou cu legătura istorică explicită.

`EvaluationAdmission` leagă candidate snapshot, evaluator/protocol/corpus refs, profil informațional, permisiunea laboratorului, dependencies/model/data policy/bugete, owner/lease/fencing/deadline. Solverul nu vede truth/scorer/canary sau soluțiile held-out; evaluatorul păstrează fixture/reset separat. Execuția unui candidat nu permite handler necunoscut, draft code import, tool neinstalat, egress direct sau build proxy respins. STATIC/PURE nu au target/provider egress; prima eval cu model cere G-MODEL/G-DATA-EARLY și acord, prima eval cu target cere gate-urile transportului și permisiunea fixture. B11/B12 nu depind de editorul complet pentru a folosi acest traseu îngust.

`EvaluationReceipt` păstrează snapshotul și **același digest** de material/index/closure, evaluator/compiler/model/tool/protocol/corpus refs, tip `STATIC_PASS/PURE_PASS/FIXTURE_PASS/BENCHMARK_PASS` ori FAIL/BLOCKED, rezultatele/limitele, evidence refs și timpii. Sunt axe distincte: STATIC_PASS verifică structură/referințe; PURE_PASS verifică pași deterministi fără ținte/model; FIXTURE_PASS cere corpus și oracle relevant: vulnerable/fixed/benign pentru SECURITY, valid/invalid/incomplete/hostile pentru CONTRACT; BENCHMARK_PASS cere protocolul held-out. O inferență contract-probe H03/G02-live nu este fixture-evaluated pentru BOLA și nu califică security coverage.

**Ordine de bootstrap nouă:** T1 Test model nu depinde de catalog/Publish. T2 folosește o metodologie minimă first-party fixată și un tool inert, fără editor general. T4 evaluează candidat IDOR/BOLA + triage + validator în PACKAGE_EVAL pe laborator autorizat, înaintea publicării SECURITY pentru producție. Seedurile STATIC/PURE B06 și CONTRACT_PROBE rămân probe istorice utile, fără a certifica pentest sau a fi relansate ca prerequisite. Dependency closure, review și caps ale fiecărui consumer rămân obligatorii.

**Un singur operator, responsabilități distincte:** autorul AI/importerul poate propune numai draft; nu primește autoritate de Review/Publish și nu își evaluează singur truth-ul. Pentru editarea manuală, operatorul unic poate confirma explicit propriul material **după** review tehnic și eval produse de checkere/evaluator independente de autorul generator; auditul înregistrează `author_kind: OPERATOR/AI/IMPORT`, actorul confirmării, receipturile și digestul. Nu cerem un al doilea cont ascuns, dar nu transformăm clickul în dovadă tehnică. Confirmarea umană este înaintea Publish și după rezultatele necesare; editul ulterior invalidează ambele. Oracolul findingului/validatorul independent rămân neschimbate.

Publish verifică atomic expected draft/candidate/review/eval revisions, eligibilitatea și exactitatea materialului, apoi face releaseul selectabil pentru **runuri noi**. Nu modifică ASSESSMENT activ și nu poate alege „latest”. Static-only poate publica knowledge fără execuție; o procedură de securitate necalificată rămâne methodology-only. Eval eșuată/receipt din alt digest/autoapprove AI/held-out leakage sunt refuzate. Eval poate fi anulată prin aceeași comandă Stop a runului de evaluare; nu aprobă publicarea. G-REVISION/G04b probează draft D evaluabil numai în lab, assessment refuză D nepublicat, D→D2 invalidează receipts și Publish păstrează D byte-for-byte după restart.

### 9.9. Pattern comun: skill, specializare și execuție

**NS01–NS08 / NS11 / NS19, din notițele originale:** acest pattern se aplică fiecărui skill de produs, nu numai `js-analyze` și `content-discovery`. **Skill ≠ agent ≠ tool ≠ procedură.** Skillul este cunoaștere/metodologie versionată; tehnica descrie metoda; procedura este o variantă bounded; toolul execută o capabilitate; copilul este o instanță temporară a unui rol Omnis care rezolvă un TaskBrief. Un copil poate folosi mai multe pachete relevante și același pachet poate servi mai multe taskuri/roluri. Parserul, fingerprintul și builderul PURE nu necesită LLM sau copil dedicat.

**Specializare la cerere:** familie → subfamilie/tehnică → procedură aplicabilă → assignment. Brainul separă taskuri când diferă ipoteza, suprafața/identitatea, capabilitatea ori independența necesară; nu creează automat câte un agent pentru fiecare skill instalat. Exemplul XSS reflected/stored/DOM/blind este o descompunere de metode, nu patru procese obligatorii sau o promisiune că toate sunt validate. Prima probă rămâne un copil, apoi plafonul comun doi; specialiștii, validatorul, researcherul și reviewerul se programează în același pool, fără fan-out imbricat acordat de pachet. Numai Brainul propune delegarea admisă; un copil returnează nevoia de specialist prin handoff.

**Authoring comun:** (1) surse versionate/licențe, scop și contraexemple; (2) obiectiv/non-goals și inputuri obligatorii/opționale; (3) mindmap/tabel al metodei și subvariantelor; (4) precondiții, tehnologii și pași; (5) unelte reale, cereri de capabilități și limite; (6) outputs/handoff, evidence și checker/oracle; (7) false positives, lipsuri, fallback, cleanup și HITL; (8) review/eval potrivite tipului → Publish. Mindmap-ul este document de authoring în references, nu DSL executabil, scheduler nou sau brain graph în UI. Matricea cerință→procedură→probă trebuie să facă vizibil ce rămâne neacoperit; adjective ca „expert” nu țin loc de metodă.

`work_kind` al tehnicii este `RECON/ANALYSIS/INVESTIGATION/VALIDATION/SUPPORT/REVIEW`. Nu este enum de permisiuni sau sloturi; de exemplu o tehnică SUPPORT poate descrie login funcțional, dar execuția rămâne la ownerul auth/B09 și la efectele sale admise. Numele ilustrative `apiInvestigator`, `authLogin`, `AuthRegister`, `CaptchaSolver`, `ClientPathExtractor`, `ContenDiscovery`, `CSPTExpert` nu sunt chei de registry sau tooluri instalate: importul le mapează explicit la chei valide și capabilități, fără normalizare tacită. Register cere efect mutator și cleanup autorizate; CAPTCHA/MFA se predau suportului uman, fără solver comercial sau bypass implicit.

| Contract de configurare / owner | Câmpuri și rezoluție (tipuri/caps §9.3–9.4) |
|---|---|
| `ExecutionPreference` / catalog sau profil | `{model_key: Key?, effort: Text?, requirement: REQUIRED/PREFERRED, on_unavailable: BLOCK/USE_RUN_DEFAULT}`; null/null înseamnă defaultul explicit al runului. REQUIRED impune BLOCK. model_key rezolvă o intrare explicit aprobată din configul providerului fixat, nu un URL/credential/model latest din prompt |
| `ProfileTemplateRef` / refs de catalog din AgentRecipe sursă | union strict `{kind: CANDIDATE, package_key: Key, entity_kind: Key, key: Key}` sau `{kind: RELEASE, ref: Ref}`; primul rezolvă numai în source_draft_refs ale aceleiași operații de freeze, al doilea numai în releaseul extern fixat. Nu este ref runtime sau acces global la drafturi |
| `AgentRecipe` / WorkflowProfileRevision.config | `{key: Key, role: enum TaskBrief sau BRAIN, package_refs: Ref[], technique_refs: Ref[], procedure_refs: Ref[], overlay_refs: Ref[], execution_preference: ExecutionPreference?, requested_capabilities: Key[], limits: Limits}`; min un pachet pentru rolurile de task. Colecția `agent_recipes: AgentRecipe[]` are chei unice; fără agents.yaml, catalog separat, proces sau tabel per recipe |
| `ExecutionSelection` / tasks + adaptor Omnis | RecordEnvelope cu `{snapshot_ref: Ref, recipe_key: Key, selected_package_refs: Ref[], requested: ExecutionPreference, effective: {provider_config_ref: Ref, model_id: Text, effort: Text?, transport_config_ref: Ref}?, resolution: NO_MODEL/EXACT/RUN_DEFAULT/EXPLICIT_FALLBACK, reason: Text, compatibility_receipt_refs: Ref[]}`; creație înainte de brief/launch, fără ref invers la brief. NO_MODEL/effective=null este permis numai la compunerea/proba inertă fără apeluri model; nu autorizează ulterior inferența. Pentru un copil AI/Brain live, effective este obligatoriu și verificat; ModelDispatch citează aceeași selection și configurație. Lipsa atestării strict cerute blochează dispatchul |

O preferință absentă se materializează explicit ca `{model_key:null, effort:null, requirement:PREFERRED, on_unavailable:BLOCK}`, nu un default personal. Seed-ul B06/P2-inert poate avea selection NO_MODEL înainte de P4a; P2-live folosește un snapshot nou configurat și selecție rezolvată, nu modifică snapshotul probei inerte. În sursa WorkflowProfile, refs de catalog din recipe folosesc **ProfileTemplateRef**, apoi CandidateSnapshot le rezolvă. Un LOCAL necalificat în profil este refuzat; nu există pachet implicit ales din ordinea package_refs. TemplateRef LOCAL din fișierele unui pachet rămâne strict în acel pachet (§9.4), iar celelalte refs de profil au schema/proprietarul declarat, nu lookup comun după key. Compilerul validează source_draft_refs fixate, unicitatea package_key în set și perechea `(package_key,entity_kind,key)`; CANDIDATE nu caută în alte drafturi sau latest. Pentru entity_kind=package, key trebuie să fie package_key. Entity kinds și types sunt aceleași ca la resolverul catalogului. Două pachete alpha/beta pot avea fiecare procedura inspect: `{kind:CANDIDATE,package_key:alpha,entity_kind:procedure,key:inspect}` și forma identică cu package_key:beta rezolvă două IDs distincte; fără package_key, cu key/tip/pachet necunoscut ori cu două revizii candidate pentru aceeași cheie, freeze este refuzat. În snapshot/publicare există numai Ref fixate cu digestul **pachetului referit**, fără selectors CANDIDATE/LOCAL rămași. Source refs sunt intrări către snapshot, nu o referință inversă în pachetele hash-uite; regulile fără ciclu §9.3/§9.8 se păstrează. **Precedență V2:** override explicit de rol → defaultul runului (§5.3); preferințele pachetelor verifică numai compatibilitatea în lista deja aprobată, fără selecție automată de cont/model. Precedența V1 care includea preferințe de pachet este numai istorică. Două preferințe de pachet incompatibile cer override explicit sau split; nu „ultima câștigă”. Un override nu încalcă cerința REQUIRED a unui pachet. Combinația se verifică înainte de Start pentru closure și înainte de assignment pentru subset; Brainul alege recipe/proceduri admisibile, nu un model arbitrar. Default absent ori model incompatibil nu devine fallback personal. `on_unavailable=USE_RUN_DEFAULT` produce receipt EXPLICIT_FALLBACK numai pentru preferință, cu motiv vizibil; schimbarea materială a configurației cere run nou.

Effort este valoarea exactă suportată de model/adaptor la revizia sa, nu un enum universal presupus `low/medium/high/xhigh/max`. Valorile și readbackul suportate sunt verificate în compatibility receipt; valoarea din sursă `xhig` este invalidă până la o alegere explicită, nu corectată tacit. Un provider care ignoră câmpul nu satisface REQUIRED. Effort nu acordă drepturi, nu mărește bugetul și nu permite acces la raționamente ascunse. Profilul poate alege același model pentru toate rolurile; alt model/provider pentru reviewer este opțiune probată, nu prerechizit BOLA.

**Inputs, context și capabilități:** argumentele sunt obiecte tipizate conform input_schema și ProcedureBinding/Step.input_bindings, nu un al doilea string `arguments` sau comandă shell. UI v1 folosește câmpuri numite; orice sintaxă pozițională ulterioară necesită parser explicit cu readback fără pierderi, fără interpolare. Secretul este handle, nu argument de prompt. Brainul citește indexul de metadata și selectează subsetul relevant; copilul primește goal/ipoteză, precondiții, non-goals, proceduri bound și context mandatory, apoi încarcă progresiv doar references/overlays din releases pin-uite și admise în assignment. Nu biblioteca întreagă, transcriptul părintelui sau memoria personală; RAG înseamnă retrieval pe aceste proiecții și refs, nu vector DB nou obligatoriu sau adevăr held-out.

Capabilitățile efective intersectează cererea recipe/procedurilor cu rolul, bindingul, scope/focus, policy/efectele, identitățile, readiness și bugetele. Încărcarea unui skill nu lărgește inventarul; o nevoie nouă se întoarce Brainului pentru assignment admis, fără schimbarea system prefix/tool schema în conversația activă. Supporting files sunt declarate/hash-uite/read-only; binary/script/config/required env dintr-un skill importat nu declanșează install, prompt de secret, passthrough de env sau execuție în home-ul personal. Code runner/shell poate exista ulterior numai ca ToolDefinition cu adaptor sandbox dedicat, I/O/resources/cancel/readback și gates; editorul nu execută cod, iar modelul nu primește terminal host/MCP wildcard/SQL direct.

**Seam SDK public, fără API imaginat:** T2 verifică Agent/Runner/Model/ModelProvider și callbackurile reale ale pinului admis. Model/config și toolset sunt construite per context din snapshotul trusted, nu prin hot-swap global. Moștenirea implicită a toolurilor este refuzată; lista goală înseamnă deny-all numai dacă adaptorul o demonstrează. Nota `allowed_toolsets=()` ca inheritance aparține exclusiv readerului Hermes V1 (§5.H), nu contractului SDK. Fără patch intrusiv în constructor/loop ori autoritate din prompt.

**Livrare G-SKILL:** B06a/b introduce numai recipe/rezoluție, support procedure și compoziție necesare seed-ului; B06m/H08 verifică requested/effective înainte de send; P4a citește configurația minimă; B11/B12 aplică patternul SECURITY; B14b adaugă editor/readback. Nu se adaugă tabele/stuburi în P0. Probe: același skill pe două taskuri distincte; două skills într-un brief fără coliziune; unknown inputs/digest/model/effort, conflicting preference, ambient tool inheritance și prompt override refuzate; lipsă tool rămâne gap, nu shell fallback. Aceste contracte v1 sunt încă neimplementate; la prima livrare se generează schema exactă, iar după publicare o schimbare incompatibilă cere versiune/migrare explicită.

### 9.10. Completitudine metodologică și rework

**NS08–NS11 / NS17–NS18:** „ai terminat metodologia?” devine verificare a obligațiilor și probelor, nu un răspuns liber yes/no. Extindem checkerele/receipts din tasks, fără serviciu sau orchestrator nou. Separăm patru întrebări: **MethodCheck/MethodReview** — ce s-a făcut din assignment; **Validation** — ce defect este demonstrat; **TechnicalReview/Evaluation de catalog** — ce pachet poate fi publicat; **ReportReview al operatorului** — ce finding CONFIRMED intră în raport. Un reviewer sever sau alt provider nu înlocuiește niciuna dintre frontierele deterministe.

| Contract | Câmpuri și reguli |
|---|---|

| `MethodReviewReceipt` / tasks | RecordEnvelope `{request_brief_ref: Ref, reviewer_result_ref: Ref, subject_result_ref: Ref, method_check_ref: Ref, disposition: ACCEPTED/REWORK_PROPOSED/BLOCKED/STALE, gap_refs: MethodRequirementRef[], reason: Text}`; persistat după rezultatul reviewerului; leagă toate versiunile fără ciclu și nu rescrie subiectul |

Un `MethodRequirement` required aparține metodei selectate, nu automat întregii biblioteci. **Applicability este calculată din predicate/probe**, nu aleasă de copil: UNKNOWN nu este NOT_APPLICABLE, input lipsă nu justifică N/A, iar un fragment JS absent nu devine „nu există”. DONE cere probele/outputurile specificate cu digest/ownership/context valide. Cerințele declarate opționale nu sunt omise: pot fi NOT_RUN cu motiv și impactul asupra acoperirii. Dacă o opțiune devine necesară pentru misiune/coverage promise, backendul materializează required=true; copilul/reviewerul nu poate elimina acea obligație. Checker indisponibil ori semantica nedecidabilă produce UNKNOWN/gap, nu un regex de tip „am terminat”.

**Succesiune:** bound procedures → MethodPlan → TaskBrief → TaskResult brut valid sau eroare de contract păstrată → MethodCheck →, dacă profilul o cere, task REVIEWER separat → MethodReviewReceipt → delta către Brain → task/attempt nou admis pentru gap. Persistăm mai întâi rezultatul pentru adresabilitate; checkerul/reviewerul nu apare în preimaginea lui. TaskAttempt.SUCCEEDED cere MethodCheck COMPLETE pentru obligațiile proprii aplicabile; altfel INCONCLUSIVE/BLOCKED după cauză, chiar dacă outputul copilului pretinde SUCCEEDED. Recepția istorică și ResultQualification din §6.3 rămân distincte. Reviewul AI este o obligație de continuare separată, nu o rescriere a stării attemptului încheiat.

`done_when` și `return_when` din TaskBrief sunt BoundPredicateRef[], fără coliziune când două proceduri au același predicate_id. Toate done_when trebuie îndeplinite pentru succes; oricare return_when poate încheia predarea bounded, fără a produce automat SUCCEEDED. `required_evidence` este MethodRequirementRef[] către cerințe care declară evidence_kinds. `stop_conditions` rămâne Key[] exclusiv în namespace-ul global trusted al core-ului fixat în snapshot; nu un lookup ambiguu în fișierul skill. Referințele se verifică față de ProcedureBinding și MethodPlan ale **aceluiași brief**. Mission criteria/bindings/outcomes rămân separate; MethodCheck COMPLETE nu produce `tested_no_issue`, CONFIRMED ori PASS funcțional fără oracle-ul și contextul cerute.

`WorkflowProfileRevision.config.method_review_policy` = `{mode: CHECK_ONLY/INDEPENDENT, required_for_roles: Role[], reviewer_recipe_key: Key?, max_rework_rounds: integer 0..3}`; Role este enum TaskBrief, excluzând REVIEWER din required_for_roles. CHECK_ONLY cere reviewer_recipe_key=null și zero rework AI; INDEPENDENT cere recipe de rol REVIEWER publicată în același snapshot și lista explicită de roluri. Profilele seed/primei BOLA folosesc CHECK_ONLY declarat; proba B18a.r pornește un run nou cu profilul/reviewerul deja publicate și pin-uite, nu injectează reviewerul într-un run CHECK_ONLY activ; profilul MVP cu review cere INDEPENDENT pentru RECON/INVESTIGATOR aleși în profil. Parser/PURE determinist fără task AI se califică prin checker, nu primește obligatoriu un critic LLM. Alegerea profilului fixează obligația de review; disable/lipsă provider nu o șterge dintr-un run activ. Nu „reviewer care review-uiește reviewerul”: propriul său output trece checker determinist de structură/proveniență.

**REVIEWER Omnis, context proaspăt și fără TARGET_IO:** primește numai subject brief/proceduri bound, result/check și proiecțiile de receipts/artifacts/excluderi relevante. Nu transcript complet, secrete, truth/corpus sau instrucțiune de a confirma. Are citiri Omnis ownership-checked și emitere rezultat; bindingul său permite explicit numai proiecțiile subject_* și input refs din review_request, nu acces generic la taskurile fraților; nu produce target probes, nu aprobă acțiuni, nu scrie catalogul, nu se autodeleagă. Investigatorul eliberează slotul înainte de review; reviewerul înainte de rework. Plafonul comun și prioritatea validatorului se păstrează. ModelDispatch purpose METHOD_REVIEW contabilizează fiecare apel și nu consumă **rezerva VALIDATION**; aceeași configurație/buget/model fixate și Stop se aplică. Același provider în context separat este admis; diversitatea modelului se evaluează, nu este dovadă de independență tehnică.

**Rework numai pe lipsuri:** Brainul consumă o dată receiptul și propune remediul sau no-op justificat; backendul verifică aplicabilitate, autoritate și buget. Nu repornim automat reconul întreg. Noul brief fixează `prior_attempt_refs` și inputurile/evidence reutilizabile numai după ResultQualification; noul rezultat citează exact probele noi. Gapul vechi se închide numai prin MethodResolution RESOLVED, relația tipizată de mai sus, nu prin existența unui nou attempt sau ACCEPTED pe alt subiect. Checkerul resolution_rule_ref este trusted/pin-uit în snapshot și verifică maparea semantică a cerințelor/procedurilor, required outputs/evidence, identitate/epoch, precondiții și inputuri materiale, nu egalitate de nume ori sugestia LLM. qualification_ref este ResultQualification a rezultatului succesor pentru assignmentul/misiunea/contextul curent; nu înlocuiește maparea cerințelor. source/result/check trebuie să fie în același run și lanț de cauzalitate admis, iar origin_requirement și successor_requirement să existe exact în MethodPlan-urile lor. successor_check_ref cere COMPLETE și cerința satisfăcătoare DONE cu probe disponibile; UNKNOWN/BLOCKED/N_A nu rezolvă o cerință originară aplicabilă. Dacă profilul cere review pentru obligația originară, successor_review_ref este obligatoriu și ACCEPTED pentru successor_result_ref, chiar dacă reworkul folosește altă specializare; în CHECK_ONLY este null. Rework rounds se contorizează pe lanțul de cauzalitate/obligația inițială, cumulativ la restart/replan/reviewer nou; schimbarea textului nu resetează limitele/stagnarea. Reviewul inițial plus maximum trei rework pot necesita cel mult patru runde de review, toate sub bugetele existente. Cap epuizat/lipsă progres → LIMITED cu gaps; efect UNKNOWN → NEEDS_RECONCILIATION. După Stop/Pause nu există review/model/rework nou; rezultate deja expediate intră numai prin receipt/reconciliere, fără wake.

**Traseu R0/C0 → R1/C1:** R0 păstrează MethodCheck INCOMPLETE și review REWORK_PROPOSED; R1 repară C1, are check COMPLETE și review ACCEPTED dacă este cerut. Backendul scrie apoi MethodResolution care leagă exact C0 de C1/R1, păstrând basis și regula de compatibilitate. Proiecția de task/plan și completion evaluează **obligația curentă** astfel: îndeplinită în rezultatul originar eligibil sau acoperită de o MethodResolution RESOLVED încă eligibilă. Astfel R0 nu trebuie să primească retrospectiv ACCEPTED/SUCCEEDED; receiptul nu rescrie R0/check/review. Toate gapurile și review-urile promise ale lanțului trebuie satisfăcute, nu doar unul. Invalidarea proof/auth/input sau bytes indisponibili produce o nouă revizie de resolution REVALIDATION_REQUIRED/INELIGIBLE și redeschide obligația în proiecția curentă a runului activ; nu reactivează un run oprit și nu rescrie rapoarte/runuri istorice. Dublă livrare aceeași mapare/payload este idempotentă; alt payload pe aceeași cheie cere conflict, nu last-write-wins. Un alt requirement/digest/epoch ori un ref cross-run nu poate închide C0.

**Reuse fără StepOutputRef cross-attempt:** dacă pasul lipsă depinde de outputul anterior, alegem fie o subprocedură publicată cu CaseSlot/ArtifactRef calificat prin ResultQualification, fie reexecutăm bounded prerechizitele necesare în noul attempt. Nu fabricăm step receipts și nu substituim outputul unui pas neexecutat în noul BoundProcedure. „Numai lipsurile” include acele prerechizite necesare; consumul/replayul rămân contorizate și cleanup-ul vechi nu dispare prin MethodResolution.

MethodCheck INCOMPLETE sau opinia GAP nu șterge un finding valid ori probe utile: candidatul complet poate merge la validator, iar campania păstrează restanțele. ACCEPTED cere MethodCheck COMPLETE, refs/probe curente și feedback fără GAP/UNKNOWN pentru cerințele required aplicabile; un „yes” de model nu acoperă NOT_RUN. Un receipt din alt result/brief/epoch invalidat este STALE. Pentru obligațiile de review promise, pending/absent/blocked rămân în predicatul de finalizare; supervisorul nu declară COMPLETED doar pentru că nu mai este copil activ. ReportReview editorial rămâne excepția separată care nu ține runul deschis.

**Handoff și HITL:** formularea „new fact/delta” din §6.1 se serializează prin observation_refs/next_clues[].basis_refs, „open items” prin gaps și method_results, cleanup prin cleanup_refs, iar inputurile folosite prin consumed_input_refs. Pentru „required context”, next_clues include `required_context: {kind: Key, reason: Text, available_refs: Ref[]}[]` — solicitare bounded, nu grant/ref inventat când lipsește inputul. Brainul construiește un nou TaskBrief după rezolvare. Needs you separă Action approval (efect exact), STEER (clarificare fără scope nou), auth asistat, disclosure/cost/tool indisponibil și ReportReview; operatorul nu este chemat prin dialog secret al copilului. Refuz/lipsă răspuns păstrează gap și limitele, nu aprobarea implicită.

**Ordine și gate:** G-METHOD-core la B06b/B11/B12 face MethodPlan/Check și predicatele calificate cu primul rezultat, fără critic suplimentar înaintea BOLA. B18a.r introduce G-METHOD **după G06a**, peste continuările existente, pentru scenariul omisiune→review citat→rework limitat→readback; B19 extinde crash/Stop. Fișierele se introduc cu consumatorul: `tasks/method_checks.py`, apoi `tasks/method_review.py` și prompt de rol în pachetul de coordonare/composer; fără serviciu/tabel dedicat în P0. Probe pozitive/negative: suport fără probe de vulnerabilitate inventate, control omis mascat prin rezumat, N/A fals, collision de predicate, alt result/digest, review indisponibil, duplicate completion, rework după Stop și buget nereînnoit. G-METHOD nu pretinde eficacitate măsurată dintr-un test Markdown.

## 10. Evidence, date și raport

**Protocol artefact:** (1) rezervare STAGING în DB; (2) scriere streaming bounded în fișier temporar exclusiv, fără nume ales de țintă; (3) flush/fsync, digest, rename atomic pe același filesystem, fsync director; (4) tranzacție DB care publică AVAILABLE plus eveniment; (5) reconciler pentru STAGING/orfani/lipsă. Cititorul verifică existența/integritatea înaintea operației probatorii. Hashul detectează modificarea, nu dovedește singur proveniența.

Stări: `STAGING`, `AVAILABLE`, `TRUNCATED`, `MISSING`, `CORRUPT`, `DELETED`; versiunea redactată este derivat cu legătură la raw. Oracle declară ce bytes sunt obligatorii; un fragment suficient poate susține o observație limitată, nu automat un verdict complet. Verdictul este refuzat dacă dovezile obligatorii sunt absente/incomplete.

Limite inițiale de fixture: request body recepționat 1 MiB; response pe wire 5 MiB; response decomprimat 5 MiB; evidence păstrat 5 MiB, ratio maxim decomprimare 20:1; artefact individual 20 MiB, 1 GiB/run. Guardul aplică bytes/time caps incremental înaintea bufferingului/decomprimării, și fără Content-Length/chunked; depășirea întrerupe consumul și închide upstreamul, nu doar trunchiază fișierul final. Pentru MVP răspunsul bounded este verificat înainte să fie predat browserului; streaming către Chromium este oprit. Trace-ul este oprit implicit și bounded când este cerut; upload OpenAPI/JS 5 MiB, depth/time limits și decodare incrementală. Memoria/CPU/PIDs/tmpfs au capuri de container, inclusiv la parser și Chromium; dumpul/trace-ul nu ocolește bugetul. Parametri ajustabili numai în revizie, niciodată nelimitat; depășirea se înregistrează, nu se ascunde. Rezervăm capacitatea înaintea unei acțiuni; disc plin oprește admiterea și păstrează starea efectului. G03a verifică bytes efectiv citiți, memorie bounded și închiderea conexiunii pe fixture chunked/decompression bomb, nu numai absența verdictului.

Inventar de date: DB, raw/derivate, seif, cookie/storageState, sessions/checkpointuri SDK, caches/traces locale și provider errors sanitizate (arhivele Hermes V1 rămân separate), screenshots, model payloads, exports și backups. Memorie globală/cloud memory/auto-learning/exporteri auxiliari dezactivate în runtime-ul de engagement. Inventarul include și queries/research artifacts/lessons/pending writes/cron outputs/curator reports/backups; numai material aprobat intră în maintenance §6.2. Providerul primește minimum necesar, conform data policy; redactarea headerelor nu garantează eliminarea PII din body/screenshot. Markeri sensibili sintetici verifică fiecare traseu în G-DATA.

**ModelProjection v1**, obligatoriu înainte de prima trimitere de date de țintă: tool results/context/delte sunt DTO-uri cu allowlist de câmpuri (ID-uri opace, metodă, cale redactată, nume/tip parametri, status, observații și fragmente bounded aprobate). Raw body, headers, query values, cookies, storageState, stack traces și fișierele de evidence nu intră implicit în context. Executorul produce o proiecție separată; secretele cunoscute se elimină, iar tipurile/câmpurile sensibile neclasificate se refuză ori cer review, nu sunt „redactate” doar prin regex general. Screenshoturile sunt dezactivate model-facing implicit; se permit doar pe fixture sintetic aprobat și după verificarea/crop/maskingului necesar. Scope-ul și proveniența proiecției sunt verificate ca la evidence read. `G-DATA-EARLY` cu markeri sintetici este înainte de G02-live pentru datele probei și înainte de P3 pentru primul output target; G-DATA la P8 extinde aceeași suită la retenție/export/restore. Nu pretindem DLP universal; sintetic-only rămâne condiție a MVP-ului.

Evidence HTML/JS/SVG se afișează ca text escapate; fără iframe raw, script, event handlers, linkuri autoîncărcate sau SVG inline de la țintă. Screenshoturi validate și decodate bounded. Download explicit cu `Content-Disposition: attachment`, `nosniff`, CSP restrictiv și avertisment; exporturile sunt offline, escapate, fără resurse remote. Nu stocăm secrete în localStorage sau URL.

Retenție default propusă: raw/derivate și sesiuni engagement 30 zile, exporturile numai explicit, audit de comenzi/snapshoturi fără payload sensibil 90 zile; secrete de sesiune numai cât sunt necesare. Ștergerea unui engagement cere run oprit, manifest de date/derivate și tombstones; backupurile expiră separat și limita este afișată. Backup consistent: run oprit/quiescent, DB + manifest artefacte + checksums; cheia seifului nu intră în aceeași arhivă. Restore într-un root separat începe locked/stopped, nu repornește taskuri și nu restaurează login AI implicit.

Finding stabil + occurrences deduplicate conservator după clasă/rădăcină/regulă/operație/context; nu unim pe titlu. Severitate argumentată separat de confidence, CWE, impact demonstrat versus potențial, pași reproductibili, evidence refs, limite, remediere și retest. CVSS numeric este opțional; dacă apare, păstrăm vectorul și calculăm determinist, fără număr inventat de LLM. Operatorul poate contesta/adnota, nu rescrie bytes sau confirma fără poarta probatorie.

Verdictul istoric și disponibilitatea actuală a dovezilor sunt proprietăți separate. La MISSING/DELETED/CORRUPT, UI și exporturile noi afișează starea curentă și replay indisponibil; nu rescriu snapshotul sau verdictul de la data lui. Exportul vechi offline nu poate cunoaște o ștergere viitoare: include data/snapshotul și avertismentul că disponibilitatea curentă se verifică în Omnis. O nouă reproducere cere probe noi; un raport vechi nu este reutilizat ca verdict proaspăt.

Promovarea unei familii ca benchmark-validated este legată de exact skill/tool/model/corpus; nu este precizie universală.

### 11.0. M-LAB — IDOR/BOLA, triage și validator

Milestone intermediar T4, nu întregul MVP/M1: URL/obiectiv/scope/identități/reguli business → discovery proprie → ipoteză/investigator IDOR/BOLA → **triage al candidatului** → validator cu attempt și auth context independente → rezultat inspectabil/readback/Stop. Triage este inițial skill al orchestratorului, nu al patrulea agent/model obligatoriu; poate prioritiza piste, dar nu acordă permisiuni și nu confirmă findinguri. Un tool result schimbă cel puțin o decizie ulterioară; agentul nu primește endpointul vulnerabil/PoC-ul/adevărul evaluatorului.

`TriageAssessmentV1` persistă candidate/evidence refs, ipoteza, precondițiile/gaps, duplicate-of ref opțional și dispoziția INVESTIGATE/NEEDS_CONTEXT/DUPLICATE/DEFER cu motiv; decizia nu șterge candidatul și nu este CONFIRMED/secure negative. Validatorul folosește metodologie fixată pentru baseline/probă/control/replay și oracle-ul BOLA determinist: principal valid, regulă DENY și date private canary corespunzătoare. HTTP 200, owner diferit sau acordul a două modele nu sunt oracle.

**Skill reuse:** conținut IDOR/BOLA, triage și validare fixat/revizuit în candidatul PACKAGE_EVAL; nu editor general ori Publish înaintea propriei evaluări. `skills/bug-bounty-triage/SKILL.md` existent rămâne QUARANTINED: original/licențe/proveniență păstrate, fără încărcare automată. Adaptarea scoate «never redact», evidence-as-authority, tool grants și escaladare în afara scope-ului; fidelitatea probelor private nu autorizează secrete în model/export. Skillul extern de validator menționat de operator este CANDIDATE_SOURCE_PENDING până primim sursa exactă/licența/revizia, apoi review și evaluare; reputația nu este calificare. Dacă nu este disponibil/admis, se folosește metodologia minimă first-party evaluată, nu se elimină validarea și nu se blochează T1/T2. Importul/adaptarea produsului au loc în felia T4, nu în T0.

Lab deținut/resetabil, date sintetice, două persoane și obiecte private plus shared legitim; variante vulnerable/fixed/benign și auth-invalid. Pozitiv: discovery și candidate triage reale, replay independent confirmă canary neautorizat. Negative: shared/owner/fixed/benign nu confirmate, auth invalid → INCONCLUSIVE, off-scope/secret/Stop refuzate. Triage, decizia validatorului, request/evidence/consum se citesc după reload/restart fără rerun. M-LAB nu cere export/report-review/retest general; acestea rămân T5/M1, iar probele de laborator nu sunt benchmark held-out sau eficacitate generală.

`JsSourceRecord` este RecordEnvelope case-scoped cu `{artifact_ref: Ref, acquisition_kind: LIVE/IMPORT/HISTORICAL, form: INLINE/EXTERNAL/LAZY_LOADED/SOURCEMAP, origin_ref: Ref?, ingested_at: UTC, retrieval_at: UTC?, archived_at: UTC?, identity_ref: Ref?, auth_epoch: integer?, parent_source_refs: Ref[], transformer_ref: Ref?, availability: enum artifact §10}`. ingested_at este timpul backendului; retrieval_at/archived_at necunoscute rămân null, nu sunt înlocuite cu timpul importului. Null identity/epoch la import înseamnă context necunoscut, nu anonymous verificat; capturile live păstrează contextul real. Ref-ul artifactului leagă bytes digest/size, iar derivatul leagă raw și versiunea transformării. Achiziția și forma sunt axe distincte: un sourcemap poate fi istoric sau live. `SourceLocation={source_ref:Ref, start_byte:integer≥0, end_byte:integer≥0}` are interval în bytes disponibil, start≤end; derivatul nu atribuie offsetul său rawului fără mapping verificat.

**Import/readback B15j.1:** owner surfaces/imports + evidence; `POST /api/v1/engagements/{id}/artifact-imports` primește command ID, expected engagement revision, `kind: JS/SOURCEMAP/JS_HISTORY`, bytes bounded și metadata de sursă strictă, fără filesystem path sau URL de fetch. `GET /api/v1/engagements/{id}/artifact-imports/{import}` citește receiptul/artifact refs/parser status/gaps după restart; source/raw se citesc prin evidence API existent, derivatele prin GET surfaces/tasks. Migrarea adaugă numai payloadul/legăturile import–artifact–source din agregatele existente. Session/CSRF/ownership/CAS/digest/path/schema/secret classification se verifică; importul este inert (zero model/target), nu pornește consumerul sau un run. Input nou într-un run activ se leagă numai engagementului propriu și este consumat ulterior prin assignment/admission nou, fără schimbarea snapshotului de cod/config. Fișierele ostile/trunchiate se păstrează private cu stare/gap, fără AVAILABLE fals; extinderea de scope prin metadata este refuzată.

`JsAnalysisArtifactV1` = artifact JSON cu schema fixată în pachet, `{schema_version:1, input_source_refs:Ref[], acquisition_gaps:Text[], coverage_state:COMPLETE_FOR_INPUTS/PARTIAL, items:{key:Key, kind:ENDPOINT/PARAMETER/API_VERSION/TECHNOLOGY/LIBRARY/FEATURE/SINK/SECRET_SIGNAL, source_refs:Ref[], locations:SourceLocation[], epistemic_state:OBSERVED/INFERRED/CONTRADICTED, details_schema_ref:SchemaRef, details:object strict, unknown_fields:Key[]}[], inferred_api_ref:Ref?, replay_recipe_refs:Ref[]}`. Schema details per kind este locală, versionată și allowlisted; nu un JSON liber model-facing. Minimum o sursă per item, maximum 128 items per shard; listă mai mare → shards/manifest bounded și truncation/gaps explicite, sub caps de bytes §10. Sursele și location refs se rezolvă numai în inputuri/derivatele autorizate; un source_ref necunoscut este refuzat. COMPLETE_FOR_INPUTS înseamnă că metoda pentru **inputurile disponibile** s-a terminat, nu că toate JS/rutele aplicației au fost descoperite.

Observat = proprietatea efectiv demonstrată: poate fi prezența unui literal într-un fișier, nu accesibilitatea rutei din acel literal. Un endpoint sugerat devine observed-live numai după Action/evidence proprii în contextul curent. API versions necunoscute, metode HTTP/auth/required params și business rules nu se deduc ca adevăr dintr-un nume. `inferred_api_ref` indică un inventar candidat pentru care păstrăm basis per câmp, contradicțiile și necunoscutele; un export OpenAPI este permis numai când câmpurile cerute de format sunt fundamentate și schema este validă, etichetat **INFERRED/PARTIAL**. Altfel exportăm inventarul parțial, nu inventăm `GET`, auth sau `servers` pentru a trece validatorul. Importul ulterior păstrează proveniența inferată și nu acordă scope/coverage; `$ref` externe rămân interzise.

Outdated libraries, sinkuri periculoase, admin/feature flags/comments și entropy/regex de secret sunt **leads**, nu exploatabilitate demonstrată. Secretul suspect rămâne artifact privat și locator/etichetă redactată; nu îl trimitem providerului sau îl încercăm ca credential. „MD Report” este vedere escapata a aceluiași rezultat, creată ulterior și legată în evidence manifest/ToolResult.artifact_refs, nu ca referință inversă în JSON-ul pe care îl redă; iar „Curl Commands” devine replay recipe tipizat/sanitizat cu handles, neexecutat automat și nerevalidat prin copiere în terminal. Anti-automation/rate-limit/auth absent produc backoff bounded, auth asistat/Needs you ori gaps; nu proxy rotation, CAPTCHA solver, browser personal sau transport direct ca fallback.

**`skills/content-discovery-wordlist/` → `skills/content-discovery/`:** două responsabilități compozabile. Primul produce date; al doilea consumă lista prin adaptor brokered. În mod determinist, builderul lucrează direct din capturi/JS results/TechnologyObservation/corpusuri aprobate sub WordlistRecipeRevision fixată. Opțional, un task **MODEL** de analiză propune candidați și priorități din același context minim; research separat poate adăuga surse publicabile înainte, numai când ajută. Nici propunerea AI și nici documentul public nu modifică recipe/codul, nu execută HTTP și nu instalează tooluri. Buget/model/effort ale propunerii sunt contabilizate, nu cost PURE ascuns.

`WordlistProposalV1` = `{schema_version:1, recipe_ref:Ref, input_refs:Ref[], technology_refs:Ref[], selected_source_refs:Ref[], candidates:{path:Text, reason:Text, basis_refs:Ref[], proposed_tier:QUICK_HIT/FULL}[], gaps:Text[]}`; maximum 128 candidați per proposal și limitele comune de bytes. Este output neîncrezător al unui task cu MethodPlan, sau input editorial revizuit; nu shell/regex/transform nou. Backendul verifică schema, path relativ admis, basis/ownership, caps, secret/PII exclusion și sursele selectate; nu pretinde că un path propus există. Input nou admis poate produce artifact nou în același run, sub recipe/model config deja fixate, fără hot-swap.

Builderul **PURE** aplică exclusiv transform_ids/ranking rules aprobate; același recipe + input/proposal bytes + seed → aceeași ordine/aceiași bytes/digest. Aceasta este determinismul generatorului, nu promisiunea că LLM-ul produce mereu aceeași propunere. Produce WordlistArtifact cu `variants: {key: GENERIC/CONTEXTUAL/FULL/QUICK_HITS, artifact_ref:Ref, entries:integer≥0}[]`, chei unice; FULL este obligatoriu, chiar gol cu motiv, iar câmpul artifact_ref existent este exact FULL. `quick_hits` este numele de prezentare pentru QUICK_HITS, subset ordonat din FULL, nu un al doilea univers ascuns. GENERIC/CONTEXTUAL pot fi goale cu motiv; FULL este reuniunea bounded/dedup conform recipe, nu promisiune exhaustivă. Provenance per candidat și counts înainte/după/excluderi/truncation sunt păstrate, inclusiv lipsa JS seed-urilor. Backendul construiește întâi bytes artifactelor variante și manifestul lor, apoi recordul WordlistArtifact care le citează; nu digest autoreferențial. Fiecare consumator fixează artifact ref/digest și varianta exactă înainte de dispatch.

Consumerul **TARGET_IO** folosește rute/fișiere generice, stack-specific, referințe JS și seeds de metodologie publică aprobate: admin/config/backup/exposed artifacts/API routes sunt ipoteze. Enumerația autorizată de paths/parametri este bounded discovery, **nu credential brute-force**. Fiecare request/redirect/control are Action/receipt, scope/focus/identity/epoch/buget/Stop; baseline soft404 este contextual și se invalidează la drift. Absența răspunsului, blocarea, zero seed, 401/403 sau zero matches nu sunt verdict sigur. O expunere candidată merge la procedura/oracolul familiei (E1 unde nesuportată); scannerul nu confirmă și nu descarcă automat secrete reale.

**Probe și reutilizare:** G-WORDLIST-CORE verifică builderul/artifactele, fără TARGET_IO sau B15 cerut înapoi; G-WORDLIST cu B15 consumă numai artifacte calificate și compară generic/contextual/quick_hits la aceleași informații și bugete, cu dedup/provenance/soft404/refuz. G-JS verifică inline/external/lazy/sourcemap/history import, schema incompletă, versiuni contradictorii, surse ostile/path escape și redacted secrets pe fixtures; nu eficacitate universală. Reuse Katana/parsers/WebTech și BBOT/CeWL/Kiterunner/Assetnote rămâne stack §10. JSLuice/Waymore/ffuf/onelistforall/DevTools sunt candidați din notițe, fără pin/adaptor/admitere inventate; alegerea concretă se probează în felia sa înainte de utilizare. Aceleași mecanisme de recipe, requirements, context, review și handoff se reutilizează pentru următoarea familie fără modificarea core-ului; o capabilitate cu adevărat nouă cere adaptor/checker și teste.

### 12.3. Reguli de import, date, API și UI

- **Direcția dependențelor:** routes/schemas → services/ports → domain. Repositories/ORM, filesystem și SDK/executor clients implementează ports și sunt conectate în `bootstrap.py`. Domain nu importă FastAPI, SQLAlchemy, SDK de agenți sau Playwright; o probă de import în CI respinge încălcările.
- **Monolit modular, nu microservicii de domeniu:** un modul folosește serviciul/portul public al altuia, nu îi modifică direct modelele. Nu introducem event bus distribuit, DI container general, `BaseService`/`BaseRepository` generic sau `utils.py` fără responsabilitate. Evenimentul durabil și idempotency rămân contracte de date, nu notificări volatile.
- **O tranzacție pentru invariantul comun:** `uow.py` deține commit/rollback; repository-urile nu fac commit pe ascuns. Admiterea autoritate/buget/approval rămâne atomică între module. SQLAlchemy session per unitate de lucru, nu globală și nu ținută deschisă cât răspunde LLM-ul. I/O async; parsing CPU și subprocessuri bounded în afara event loopului.
- **Boundary strict:** input validat cu DTO-uri, erori tipizate și correlation ID; UUID-uri opace, UTC, entity revisions, ownership engagement-scoped, paginare bounded. Nu returnăm ORM, traceback, env sau secrete. Domain errors sunt mapate explicit la contractul HTTP, inclusiv 409 și stări necunoscute.
- **Contracte generate:** API-ul este sursa pentru `contracts/omnis.openapi.json` și apoi `web/src/shared/api/generated.ts`; schema internă pornește din DTO-urile interne ale aceluiași cod. CI detectează drift; nu edităm generated types de mână și nu generăm cod din OpenAPI-ul țintei. Wire schema are versiune și compatibilitate verificată între mediile separate.
- **Frontend:** TypeScript strict, Router pentru navigare/filtre/selecție, Query pentru server state, state local numai pentru draft/interacțiune. CSS Modules + tokenuri generate din DESIGN; Radix pentru interacțiuni complexe și HTML nativ unde ajunge. Fără `any`/ignore global/catch gol pentru a face testele verzi; stările loading/empty/error/stale/unknown rămân distincte.
- **Date și loguri:** ID-uri/cauzalitate în logs structurate, allowlist/redaction înainte de log/model/export; nici evidence raw, tokens, cookies sau codes de pairing în browser storage/URL/log. Bloburile nu se servesc prin director static; numai endpoint cu ownership, integritate și policy. Settings runtime nu este filesystem browser.
- **Config și dependențe:** manifeste/lockuri separate pentru web, API/supervisor, CLI și fiecare executor; closure Hermes numai istorică; nu un venv comun. `api/src/omnis/core/config.py` și `cli/src/omnis_cli/config.py` au subseturi proprii tipizate, nu copiază credentiale. Versiunile sunt cele din stack baseline; formatare/typecheck/dependency audit se fixează explicit în B01a, nu alegem aici versiuni inventate pentru unelte lipsă.

### 12.4. Comenzi și traseul unei felii

Astăzi `make check`/`make test` acoperă documente/unelte, API/control PostgreSQL și bootstrapul web. `make check-api`, `make test-api`, `make test-migrations`, `make check-api-wheel`, `make check-web`, `make lint-web`, `make typecheck-web`, `make test-web`, `make build-web`, `make test-contracts` și `make test-e2e` sunt implementate. E2E servește buildul real prin API și folosește numai coduri sintetice prin controlul privat. **Comenzi viitoare, nu deja funcționale:** `make dev`, `make build`, `make test-safety`, `make test-release`; se adaugă odată cu componentele lor. Un gate indisponibil raportează NOT-RUN/BLOCKED, nu exit 0. CI apelează aceleași comenzi locale; CI remote nu a fost executat. Launcherul instalat `omnis` rămâne P0.4, nu este înlocuit cu Vite sau Make.

Exemplu B02: test domain RED → modul `engagements` + migrare → repository pe PostgreSQL real → route/DTO/OpenAPI → tipuri generate + formular/query web → E2E create/reload/conflict → commit coerent. B07 adaugă policy/evidence cu aceleași frontiere, nu un director generic de „agenți” care ajunge să dețină DB și rețeaua. Corpul held-out/scorer rămâne într-un workspace evaluator separat, niciodată montat runtime-ului.

Migrațiile se execută o singură dată prin comandă dedicată înaintea startupului; schema incompatibilă blochează readiness. Backup înaintea migrațiilor distructive; rollback documentat sau restore, nu promisiune că orice migrație este reversibilă. CI fără secrete/scanări/LLM: format/typecheck/unit/contracts/build, DB reală de test, safety fixtures izolate. Live provider opt-in și buget explicit.

TDD pe felii verticale: test RED relevant → implementare minimă → GREEN → refactor. Commit mic per comportament/decizie, numai fișiere intenționate, mesaje cu motiv și verificări. Upgrade SDK/dependințe prin schimbare explicită, lock/digests, contract+safety suite, fără upgrade sub run activ. Nu încărcăm automat pluginuri/pachete din rețea la startup.

### Porți de decizie care rămân reale, nu ascunse

- **G-RUNTIME:** identitate task/attempt/rol, tool loop, checkpoint/inbox, credential ownership și Stop pe biblioteca/transportul nou; lipsa seamului sigur blochează consumerul, nu autorizează runtime alternativ ori identități false.
- **G-DEPENDENCIES:** proxyul publicat cu dependențe afectate rămâne respins; B01e-build permite numai testarea unui build remediat în harness izolat autorizat. B01e-integrated în B07/B09 + G-NET închid admiterea de assessment; nu cerem proba integrată înainte să existe adaptorul care trebuie testat.
- **G-NET:** proxy/namespace nu poate împiedica toate traseele certificate — transport blocat; nu activăm fallback direct.
- **G-PROVIDER:** cont, model, entitlement, buget și data policy aprobate — test live blocat până atunci; P0/P1 și testele fără LLM continuă.
- **G-RELEASE:** toate funcțiile MVP promise, inclusiv Settings complet/ambii provideri, au dovezi. Lipsa contului nu devine succes mock.

Acestea sunt condiții de execuție ale planului, nu alegeri de stack lăsate fără proprietar. Raportul de re-review consemnează ce a fost verificat în această livrare și ce trebuie demonstrat de aplicație.
